# 카메라로 품목 등록하기

재고 입력 권한이 있는 직원은 급식길의 **재고 관리 → AI 스캔 등록**에서 상자나 포장을 촬영할 수 있다. **직접 입력**을 누르면 기존 등록 화면이 열린다. 두 방식 모두 직원이 실제 입고 수량을 확인한 뒤 같은 서버 저장 절차를 거친다. [급식길 열기](https://onnuriway.com)

## 창고에서 사용하는 순서

1. 한 품목의 이름이 인쇄된 상자, 포장 라벨 또는 바코드를 비춘다. 중앙의 포장이 얼마나 선명하고 안정적으로 보이는지에 따라 조준선과 전자음이 바뀐다. 촬영 버튼을 한 번 누르거나 길게 눌러 원을 채우면 촬영된다. 누르던 손가락을 밖으로 옮기면 취소되고 사진을 확보한 순간 상승음이 난다. 소리는 끌 수 있다. 기기 카메라, 앨범, 바코드 번호 입력도 사용할 수 있다.
2. 급식길에 연결된 바코드면 기존 품목과 포장 단위가 표시된다. **이 품목 입고하기**로 새 입고를 기록한다. 사진을 찍으면 AI가 포장의 글씨와 제품 모양을 살펴본다. 정식 제품명이 흐려도 외형에서 제품 종류를 알아볼 수 있으면 **AI 제품 추정**에 이름과 단서가 표시된다. 직원이 **이 이름 사용**을 눌러야 초안에 들어간다. 식품안전나라 후보는 별도로 대조할 수 있다. 출처가 다른 이름은 직원이 같은 품목인지 확인한다.
3. 제품명이 적힌 앞면과 내용량·소비기한이 적힌 뒷면을 이어 찍을 수 있다. 최대 세 장을 함께 보며 확대해 대조하고, 사진을 제외하면 한 장 더 찍을 수 있다. 사진을 추가해도 직접 고치거나 지운 내용이 유지된다. 대표 사진을 명시적으로 선택한 경우에만 기존 품목 사진 업로드가 실행된다.
4. 제조사는 사내 제조사 목록에서 확인한다. 박스 입수와 이번 입고의 소비기한은 각각 적용 버튼을 눌러 확인한다. 실제 수량과 보관 장소를 확인하고 **품목 등록**을 누른다. 서버가 품목과 첫 입고 저장을 확인하면 완료 화면에서 다음 제품을 스캔할 수 있다.

운영자는 **재고 관리 → 설정 → 보관 장소 담당자**에서 냉장·냉동1·냉동2·샘플 담당자를 지정하거나 해제한다. 스캔할 때 직원의 담당 장소가 먼저 선택되며, 신규 등록과 기존 품목 입고 모두 저장 전 바꿀 수 있다. 한 직원이 여러 곳을 맡으면 현재 목록에서 보고 있는 담당 장소를 우선하고, 전체 목록에서는 냉장·냉동1·냉동2·샘플 순서로 선택한다. 미지정 직원은 보고 있는 장소로 시작하고 전체 목록의 기본값은 냉장이다.

카메라 권한은 스캔 화면을 처음 열 때 휴대전화에서 요청한다. 접근이 거부되면 **카메라 권한 설정 방법**에서 Android Chrome과 iPhone Safari의 설정 경로를 확인할 수 있다. 설정을 바꾼 뒤 **카메라 다시 열기**를 누르거나, **앨범**과 **번호 입력**으로 계속한다. 스캔 화면을 닫거나 앱이 백그라운드로 가면 카메라를 끈다. [Chrome 카메라 설정](https://support.google.com/chrome/answer/2693767?hl=ko&co=GENIE.Platform%3DAndroid) · [Safari 웹사이트별 카메라 설정](https://support.apple.com/ko-kr/guide/iphone/-iphb01fc3c85/ios)

| 포장 또는 현장 정보 | 등록 결과 |
| --- | --- |
| 상자에 제품명만 적힘 | 읽힌 이름으로 초안을 시작한다. 급식길의 유사 품목과 공공 목록에서 대조할 수 있다. |
| 한 봉 750g, 25g × 30개 | 규격에 한 봉의 내용량과 봉 안의 구성을 함께 표시한다. |

| 실제 도착 2박스와 낱개 1봉 | 직원이 입력한 계산으로 이번 입고에 17봉을 반영한다. |
| 소비기한 2027.02.17 | 날짜와 근거를 표시하고 직원이 확인하면 이번 입고 묶음에 적용한다. 다음 입고는 새 날짜를 받는다. |
| 제조일만 표기, 소비기한 별도 표기, 제조 후 12개월 | 실제 날짜를 추가 촬영하거나 직접 입력한다. 확인할 수 없으면 ‘미확인’을 선택한다. |

## 촬영과 조회의 설계

- WAiNQ는 시작 탭에서 오디오를 켜고, 대상과 조준점 사이의 거리와 홀드 경과에 따라 음높이와 반복 간격을 바꾼다. 포착하면 별도의 상승음을 낸다. 급식길은 중앙 영상의 명암·질감·흔들림으로 조준음을 조절하고, 길게 누르면 손가락을 댄 실제 시간에 맞춰 링과 전자음이 빨라진다. 한 번 눌러도 촬영할 수 있다. 사진 확보, AI 응답, 서버 저장 완료를 각각 표시한다. [WAiNQ](https://wainq.bang.kim/)
- 여러 면에서 읽은 필드를 합치고, 값 옆에 출처와 원문을 붙였다. 애매한 제조사와 수량은 사진을 확대해 확인할 수 있다. 수동 촬영과 추가 촬영, 이미지 근거를 남기는 검수 방식을 참고했다. [Scandit Label Capture](https://docs.scandit.com/sdks/android/label-capture/advanced/) · [Apple 문서 스캔](https://support.apple.com/en-us/108963) · [Open Food Facts 앱](https://github.com/openfoodfacts/smooth-app) · [Robotoff](https://github.com/openfoodfacts/robotoff)
- 기기에서 EAN-8·13, UPC-A·E, ITF-14를 판독한다. 숫자의 검증 자릿수를 확인하고 14자리 GTIN으로 비교한다. 직원이 봉·박스 중 포장 수준을 선택해 연결한다. 서로 다른 코드가 함께 보이면 한 번호로 확정하지 않는다. [Grocy](https://github.com/grocy/grocy) · [GS1 포장 단계와 GTIN](https://ref.gs1.org/guidelines/2d-in-retail/)
- 단일 사진을 메모리에서 방향 보정하고 긴 변 최대 2400px JPEG로 처리한다. OpenAI Responses API에 이미지 한 장과 엄격한 출력 스키마를 보낸다. 이미지 상세도는 high, 추론 강도는 low, 응답 저장 옵션은 false다. 서버가 날짜, 출처 문구, 박스 단위 등 반환값을 다시 확인한다. [OpenAI 이미지 입력](https://developers.openai.com/api/docs/guides/images-vision) · [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

## 식품안전나라 연동과 운영 설정

카메라 판독에는 서버의 기존 `OPENAI_API_KEY`를 사용한다. 기본 모델은 `gpt-6-luna`이고, Functions 환경의 `INVENTORY_SCAN_OPENAI_MODEL`로 교체할 수 있다. 식품안전나라 계정 등록은 공공 제품 후보 조회를 사용할 때 필요하다. 사내 바코드 조회와 사진 판독은 별도로 동작한다.

1. 식품안전나라 데이터활용서비스에서 인증키를 발급받고, **바코드연계제품정보 C005**와 **식품(첨가물)품목제조보고 I1250** 각각의 OpenAPI 이용을 신청한다. 서비스별 이용 신청 누락은 기관의 `INFO-110` 응답으로 구분된다. [C005 신청 및 명세](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=C005) · [I1250 신청 및 명세](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=I1250)
2. 운영 반영 시 서버 Secret Manager의 `FOODSAFETY_API_KEY`에 키를 설정하고 Functions의 `INVENTORY_FOOD_LOOKUP_ENABLED=true`를 적용한다. 이 플래그를 Firebase 배포 소스 분석과 런타임 양쪽에 제공해야 해당 조회 함수에만 키가 연결된다. 발급 전에는 플래그 기본값 false로 운영할 수 있다. 키를 브라우저 공개 변수에 넣지 않는다.
3. 릴리스 범위는 Hosting 화면, 기존 `saveInventoryProduct` 갱신, 새 Callable 5개, Firestore의 필드 인덱스·TTL 정책이다. 새 함수는 `analyzeInventoryProductLabel`, `lookupInventoryBarcode`, `bindInventoryProductBarcode`, `searchInventoryFoodProducts`, `recordInventoryRegistrationOutcome`이다. 운영에서는 기존 재고 쓰기 권한과 App Check를 사용한다. 판독과 공공 조회 함수 각각에 필요한 Secret 접근을 확인한다.

공공 조회는 유통 바코드 일치 여부와 생산중단·폐업 또는 생산종료 상태를 확인한다. 검색 결과는 최대 6개까지 보여준다. 제품명이 비슷하거나 제조사가 여럿이면 직원이 후보를 고른다. 공공자료에 ‘제조일로부터 12개월’이라고 적혀 있으면 이번 입고분에 찍힌 실제 소비기한을 별도로 확인한다. 공개 샘플로 생산중단된 제품이 후보에서 제외되는지 확인했다. 현장에서 쓰는 제품 중 몇 퍼센트가 공공 목록에서 찾아지는지는 실사 때 측정할 항목이다.

### 식품안전나라 조회 개통

2026년 11월 28일 식품안전나라에서 급식길의 사내 제품 조회 용도로 C005와 I1250 사용 승인을 받았다. 발급 키는 Google Cloud Secret Manager의 `FOODSAFETY_API_KEY` 버전 1로 보관한다. 서울 리전의 조회 함수 `searchInventoryFoodProducts`를 먼저 배포했다. 운영 리비전은 `searchinventoryfoodproducts-00001-vux`다. [식품안전나라 인증키 신청·이용약관](https://www.foodsafetykorea.go.kr/api/newUserApiAplcKey.do) · [서비스 신청 현황](https://www.foodsafetykorea.go.kr/api/newUserApiAplcDtl.do)

- 실제 키로 바코드 `8801791000192`에서 ‘쌈장용된장’ 한 건을 확인했다. 제품명 ‘고기만두’는 서로 다른 후보 여섯 건을 반환했고 추가 결과도 있었다. 같은 운영 코드를 사용한 데모 직원 세션에서도 두 조회가 성공했다. [바코드연계제품정보](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=C005) · [식품(첨가물)품목제조보고](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=I1250)
- 두 서비스에 동시에 요청했을 때 기관이 인증키 사용 중(`INFO-500`)을 반환했다. 이 조회 함수는 요청을 한 건씩 처리하고, 같은 오류가 오면 0.6초 후 한 번 재시도한다.
- 운영 주소는 앱 인증을 거치며 익명 요청에 `401 UNAUTHENTICATED`를 반환했다. 배포 소스와 검증한 패키지의 핵심 파일 7개가 일치했다. 재고 회귀 테스트 562개가 통과했다.

### 2026년 11월 28일 카메라 등록 운영 배포

15시 54분(한국 시각)에 급식길에서 카메라 등록을 열었다. 앱 버전은 `2026-11-28.1`, Firebase Hosting 버전은 `d4ca9cdc4127ede5`다. 직전 Hosting 버전은 `b1723bd686af1e2f`다. 운영 도메인과 Firebase 기본 도메인에서 내려받은 파일 171개가 각각 검증 빌드와 바이트 단위로 일치했다. [기능 변경 내역](https://github.com/kim-DL/ONWAY/pull/28)

- 최종 커밋 `d4142af`의 필수 CI 검사 14개가 통과했다. 배포 전에는 가상 카메라에서 권한 거부 안내, 권한 변경 후 재시도, 실제 비디오 트랙 열기와 해제를 확인했다. [CI 검증 결과](https://github.com/kim-DL/ONWAY/actions/runs/46117007794)
- 브라우저 업무 검증에서 박스당 8봉을 확인한 뒤 2박스와 낱개 1봉을 입력하자 재고에 17봉이 반영됐다. 별도로 배포용 서버 패키지를 Firebase 에뮬레이터와 실제 OpenAI API에 연결했다. 합성 만두 포장에서 박스당 8봉을 읽었고, 17봉 입고 요청을 두 번 보내도 한 건만 저장됐다. 다른 품목에 같은 바코드를 연결하려는 요청은 충돌로 처리됐다.
- 서울 리전의 사진 판독, 사내 바코드 조회·연결, 등록 지표, 품목 저장 함수 5개에서 새 리비전이 요청을 받는 것을 확인했다. 운영 소스 파일 46개가 검증 패키지와 일치했고, 각 함수는 미인증 호출에 `401`을 반환했다. 스캔 판독 요청 1일, 일일 사용량 2일, 등록 지표 90일의 Firestore 자동 만료 정책도 모두 활성화됐다.

### 조준음·사진 추정·담당 장소 적용

2026년 11월 28일 21시 33분(한국 시각), 앱 `2026-11-28.2`를 배포했다. 급식길 운영 도메인과 Firebase 기본 도메인에서 각각 내려받은 파일 172개가 검증 빌드와 일치했다. Firebase Hosting 버전은 `eecce515e43434cb`다. [변경 내역](https://github.com/kim-DL/ONWAY/pull/30) · [CI 검사 14개](https://github.com/kim-DL/ONWAY/actions/runs/46143228687)

- 이전 버전에서 카메라가 열린 뒤 소리를 준비하면 브라우저가 첫 탭을 놓쳐 전자음이 재생되지 않는 현상을 재현했다. 수정 후 브라우저에서 첫 탭의 오디오 파형을 측정했다. 길게 누르는 도중 취소하면 사진이 전송되지 않았고, 끝까지 누르면 한 장이 촬영됐다. 창고 소음 속에서 직원 휴대전화의 소리가 충분히 들리는지는 실사 때 확인할 항목이다.
- 배포용 사진 판독 함수를 실제 OpenAI API에 연결했다. 제품명이 없는 커피 사진에는 ‘커피’와 잔 안쪽의 색을 단서로 제안했고, 단색 이미지에는 제품 후보를 내지 않았다. [검증에 쓴 공개 사진](https://raw.githubusercontent.com/scikit-image/scikit-image/v0.25.2/skimage/data/coffee.png)
- 로그인한 운영자가 담당 장소 세 곳을 저장하고 설정을 다시 열어 서버의 배정을 확인했다. 에뮬레이터에서는 담당자가 스캔을 열면 해당 장소가 선택되고, 새 품목과 기존 바코드 입고 모두 이번 입고 장소를 바꿀 수 있었다. 일반 직원의 담당자 변경 요청은 거절됐다.
- 단위 테스트 2,200개와 Firestore 통합 테스트 16개가 통과했다. 조건부 단위 테스트 26개는 제외됐다. 운영 서버에서는 재고 화면 정보, 담당자 조회·저장, 사진 판독 함수 네 개가 검증한 소스로 요청을 처리하는지 확인했다.

## 비용과 검증

실제 API에 합성 한글 포장을 보냈다. 1100px 시료 세 장에서 Luna가 ‘들깨수제비’의 750g·봉 안 30개·박스당 8봉을 구분했다. 수입제품에서는 판매업체를 제조사로 채우지 않았고, 인쇄명만 있는 상자에서는 ‘단호박 미니전’만 반환했다. 각 응답은 1.6~4.9초였다.

## 첫 운영 배포 때 로컬에서 확인한 범위

- 최종 단위 테스트 2,197개가 통과했고 조건부 테스트 26개는 제외됐다. TypeScript, ESLint와 Functions 빌드도 통과했다.
- 데모 Firebase 설정으로 앱을 운영 모드로 빌드하고 PWA와 성능 검사를 통과했다. 카메라 등록 코드는 스캔을 열 때, 보조 바코드 판독기는 브라우저의 기본 판독기가 번호를 읽지 못했을 때 불러온다. gzip 기준 재고 화면은 26,064바이트, 스캔 등록은 17,201바이트, 보조 판독기는 15,573바이트였다. 등록 방식 선택 버튼을 위해 재고 화면 예산은 128바이트 늘렸다.
- 브라우저 업무 시나리오 6개에서 가상 카메라로 두 면 촬영, 실패한 사진 재판독, 수정 유지, 박스 단위 저장과 재입고, 대표 사진 한 장 저장, 직접 등록, 읽기 전용 권한, 오프라인 복구를 확인했다. 외부 판독과 공공 후보 응답은 지정된 값으로 대체했다. 로그인과 데이터 저장은 Firebase 에뮬레이터를 사용했고, 실제 OpenAI 판독은 위의 별도 실험에서 측정했다.
- Firestore 에뮬레이터 통합 테스트 16개가 통과했다. 같은 바코드를 두 품목에 동시에 연결하는 경우, 재판독 중복 요청, 사용량 한도와 접근 권한을 검사했다.
- 재고 관련 테스트는 `npm run test:inventory`, 인증과 저장까지 잇는 브라우저 검증은 `npm run test:e2e:inventory`로 실행한다.

## 데이터와 개선 지표

제품·첫 입고·사진 연결·바코드 연결과 요청 영수증은 기존 Firestore 트랜잭션에서 함께 확정한다. 다른 품목이 같은 바코드를 선점하면 처음 시도한 제품과 수량도 생성되지 않는다. 기존 품목에 대한 바코드 연결은 별도 확인 후 감사 이력을 기록하고 입고 수량은 기존 입고 화면에서 처리한다.

판독 사진은 세션 메모리에서 다룬다. 서버는 중복 과금을 줄이기 위해 요청 ID, 직원 계정, 입력 해시, 상태와 판독 결과를 보관한다. 판독 요청은 1일, 일일 사용량은 2일 TTL 대상이다. 같은 사진 요청은 준비된 결과를 다시 이용한다. 실패가 확인된 사진은 직원이 판독을 다시 눌렀을 때 재시도할 수 있다. 재시도를 포함해 일별로 직원 60장, 회사 250장을 제한한다. 직원이 선택한 대표 사진에는 기존 비공개 사진 보관 정책을 적용한다.

`companies/onnuri/inventoryRegistrationMetrics`에는 방식, 등록·입고·중단 여부, 전체·판독 대기·검토 시간, 촬영 수, 제안한 필드명과 최종값이 달라진 필드명을 최대 90일 TTL 대상으로 기록한다. 사진, 품목명, 바코드와 직원 이름은 지표에 담지 않는다. 필드 차이에는 직원이 후보를 채택하지 않은 경우도 포함된다. 직원이 명시적으로 닫은 세션을 중단으로 기록하며, 브라우저 강제 종료는 집계에서 빠질 수 있다.

현장에서는 직원 3명이 같은 제품군을 직접 입력하고 스캔한 건의 **등록 완료까지 걸린 시간 중앙값**을 먼저 비교한다. 제조사 후보의 수정·미채택 비율, 기존 품목 입고로 마친 건, 재촬영 수, 소비기한 후보를 얻은 비율을 함께 본다. 반사 비닐·구겨진 박스의 초점, 냉동창고 소음 속 효과음, 실제 iPhone·Android 기기의 사용성, 식약처 키를 사용한 급식 전용 제품 조회율은 실물 검증이 남아 있다.
