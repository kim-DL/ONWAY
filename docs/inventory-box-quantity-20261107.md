## 사용자에게 달라지는 동작

- 상품 등록·정보 수정에 선택 항목 ‘박스 입수 수량’을 추가했다. `1박스 = 10봉`처럼 기준 단위와 함께 표시한다. 모르면 비워둘 수 있으며, 기존 상품의 기본 상태는 미등록이다.
- 입수량이 있는 상품은 초기 수량·입고·출고·조정·이동 화면에서 박스 계산으로 열린다. 박스 수와 낱개를 입력하면 총수량을 바로 표시한다. 총수량 직접 입력으로 전환할 때 유효한 수량을 보존한다.
- `3박스 × 10봉 + 2봉 = 32봉`으로 계산한다. 낱개는 해당 상품의 기준 단위를 뜻한다. 봉 내부의 개수와 박스 안의 봉 수는 혼동하지 않는다.
- 수량 화면에서 박스당 수량을 바꾸면 해당 계산에만 적용된다. 상품 기본 입수량 변경은 정보 수정에서 한다.
- 잘못된 수량, 소수, 음수, 범위 초과, 재고보다 많은 출고는 저장하지 못한다. 빈 입력과 명시적인 0을 구분한다.
- 상품 상세에 박스 입수량을 표시한다. 박스 계산으로 저장한 신규 입출고 기록에는 당시 계산값도 표시한다.
- 신규 등록에서 박스 계산 후 상품 기본 입수량을 바꾸면 초기 수량을 다시 확인하도록 비운다. 이전 환산값으로 잘못 저장하지 않는다.

## 기존 데이터와 계약 보존

- 기존 `unitLabel`, `unitsPerBox`, 재고 수량, 유통기한별 재고, 과거 이벤트를 변환하지 않는다. 운영 데이터 마이그레이션도 없다.
- 새 `boxPackSize?: number | null`은 편집 가능한 포장 정보다. 입출고 이력이 있는 상품의 기존 단위 변경 제한은 유지한다.
- 구버전 클라이언트가 `boxPackSize` 없이 상품을 수정하면 저장된 값을 보존한다. 명시적 null만 미등록으로 바꾼다.
- 입수량 변경 시 상품 revision과 stockRevision을 갱신하여 이전 정보를 사용한 수량 저장을 충돌 처리한다. 기존 실사 확인·수량·날짜·이력은 유지한다.
- 새 `packageQuantity`에는 박스 수, 당시 박스당 수량, 낱개를 담는다. 서버에서 정수·범위·합계 일치를 검사하고 실제 변경과 동일한 트랜잭션으로 이벤트에 남긴다.
- `includePackaging`을 요청한 클라이언트에만 새 포장 필드를 응답한다. 중첩 상세·이벤트에도 같은 필터를 적용하여 구버전의 엄격한 스키마 검사를 보존한다. 응답 선택 플래그는 저장 요청 fingerprint에서 제외한다.
- Callable/App Check/권한/세션 재확인, request ID 중복 방지, revision 충돌, 서버 저장 확인 후 완료, 감사 이력을 유지한다.

## 배포 시 유의점

2026-11-07 사용자가 최종 점검 후 운영 배포를 명시적으로 승인했다. 아래 검증과 운영 배포를 완료했으며 실제 배포 결과는 별도 릴리스 기록에 남겼다.

- 최종 코드 검토에서 제조사 연결 처리 시 구버전 요청에 생략된 박스 입수량이 유실되는 경로를 발견했다. 먼저 재현 검사 실패를 확인하고, 보존된 draft를 사용하는 수정 후 재고 검사 535개를 통과했다.
- 전체 단위 1,886개 통과 후 위 보완에 대한 재고 535개를 재검증했다. 최종 박스 계산 브라우저 10개, 실제 Callable 상품 등록·입출고·사진 교체 흐름 1개, 격리 Firestore 트랜잭션 검사 13개 통과. 마지막 검사는 기존 재고/이력 보존, 잘못된 계산 거부, 동시 재시도 시 1회 반영을 포함한다.
- 최종 타입/lint, Functions·Hosting 빌드, PWA·Hosting 검사를 통과했다. 최종 CSS는 30,878B raw / 7,050B gzip이다. 내부 단위·포커스 프레임·선택 색상 후속 조정으로 raw 한도가 초과하여 재고 전용 raw 예산을 30.5KiB로 맞췄고, gzip 7KiB 및 모든 초기 자산/JS 예산은 유지했다. 최종 성능 검사 통과.
- 배포 전후 운영 상품 92개, lot 89개, 이벤트 240개의 문서별 해시가 모두 일치했다. 원문·개인정보·인증 정보를 증거 파일에 저장하지 않았다.
- 배포 대상: `listInventoryProducts`, `getInventoryProduct`, `saveInventoryProduct`, `recordInventoryMovement`, `recordInventoryCount`, `updateInventoryLot`, `setInventoryProductStatus`, `deleteInventoryProduct`, `listInventoryHistory`. 사진 함수는 개별 필드만 읽어 새 포장 필드와 충돌하지 않으므로 대상에서 제외한다.

승인 후에는 **재고 관련 Functions를 먼저 호환 버전으로 배포하고 Hosting을 배포**해야 한다. Hosting만 먼저 올리면 기존 서버의 strict 입력 검사가 `includePackaging` 등을 거부한다. 상품·이벤트를 읽거나 쓰는 관련 함수 전체가 새 필드를 처리할 수 있어야 한다. 실제 배포 대상 목록은 승인 후 export와 의존성을 대조해 확정한다.

Hosting 명령은 `--project onnuriway --only hosting:onnuriway` 범위를 지킨다. 기존 납품사진 IndexedDB v2 호환도 유지해야 한다. 새 포장 정보가 저장된 뒤 서버를 이 필드를 모르는 버전으로 단순 복구하면 엄격한 문서 파싱이 실패할 수 있으므로, 서버 복구는 새 필드를 읽고 보존하는 호환 버전으로 한다. 기존 이벤트·수량을 지워서 복구하지 않는다.
