# 재고 업무 즉각성 검증

상태: 로컬 구현·동일 조건 반복 측정·최종 회귀 및 빌드 검증 완료. 운영 배포 없음.

## 의사결정 요약

- 주요 병목은 목록 행의 사진 요청 경쟁, 검색 때 반복되는 정규화·실사 계산, 첫 등록 폼의 코드 준비와 modal layout, 사진 Base64의 동기 변환이었다.
- 1,000개 합성 상품의 p75에서 상세 첫 정보 표시 2,028→160ms, 최신 상세 확인 2,036→285ms, 첫 등록 입력 준비 797→346ms, 중간 상품 검색 123→19ms였다. 첫 목록 행은 1,521→1,512ms로 사실상 유지됐다.
- 목록 사진 POST 18→0회, 사진 수신 749,682→0B. 전체 목록 구간 수신량은 100개에서 86.3%, 1,000개에서 46.6% 감소했다. 유효 60초 snapshot의 재진입 context/list 요청은 계속 0회다.
- lab INP 추정 p75는 1,000개 224→176ms, 100개 152→192ms다. 작은 목록 조건의 악화를 숨기지 않으며 두 조건 모두 200ms 이하다. 이 수치는 실사용자 INP나 Galaxy 실기기 결과가 아니다.
- 촬영 fixture의 첫 미리보기 p75는 1,000개 415→372ms였지만 촬영 경로는 그대로다. 제한 회선에서 사진 표시 약 7.1초·사진 포함 저장 확정 약 19.1초가 남는다. 저장 첫 paint가 일관되게 개선됐다는 근거는 없으며 codec 변경의 효과는 이후 준비 작업과 긴 작업 감소다.
- 기본 page size 100·60초 TTL·기존 인증/재시도/감사 계약을 유지했다. 첫 40건 실험은 초기 검색 누락으로 폐기했다. Worker, 상시 인스턴스, 선행 데이터/사진 요청, 운영 배포는 도입하지 않았다.
- 아래 모든 반복 비교는 고정된 측정 버전의 수치다. 이후의 작은 용량 정리는 별도로 명시하며, 실제 카메라·설치 PWA·Cloud Functions cold start는 미측정으로 남긴다.

## 판단 기준

- 버튼 반응과 서버 저장 완료를 구분한다. INP는 입력부터 다음 화면 표시까지의 지연이며 서버 왕복 전체 시간이 아니다. 입력 대기·이벤트 처리·표시 지연을 나눠 본다. 목표는 p75 200ms 이하다. [web.dev INP](https://web.dev/articles/inp), [최적화 지침](https://web.dev/articles/optimize-inp)
- 브라우저 CPU 제한은 이 컴퓨터 대비 배율이며 Galaxy 실기기의 성능을 재현한 것으로 간주하지 않는다. 자동화 동작의 대기·스크롤 비용도 실제 입력 이벤트 지연과 구분한다. [Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference)
- 이 앱은 Next 정적 내보내기와 화면 내부 모달을 사용한다. 실제 설치된 Next 문서와 기존 React lazy 경계를 기준으로 입력 폼 코드의 유휴 준비를 실험한다. 데이터나 사진을 숨은 화면에서 미리 요청하지 않는다. [React lazy](https://react.dev/reference/react/lazy)
- Emulator 실행 시간은 Cloud Functions의 실제 cold start가 아니다. 실제 cloud cold start 기여도는 **미측정**이다. 상시 인스턴스·유료 인프라 변경은 하지 않는다. [Firebase 성능 지침](https://firebase.google.com/docs/functions/tips)

## 서버 사진 처리

저장소 전체의 original/originalUrl/originalPath/variant 참조와 클라이언트·Functions·Storage 정리·감사·관리 코드·테스트를 대조했다. 재고 계약은 thumbnail/preview만 읽고 쓰며 기존 코드가 만든 original은 메모리에서 버려졌다. 학교 사진의 original 소비자는 존재하므로 해당 경로는 유지했다. 기존 Storage 객체 삭제·이전은 없다.

재고 전용 처리 함수가 thumbnail과 preview만 생성한다. 크기·WebP quality·effort·smartSubsample·orientation 처리를 유지했다. [Sharp 출력 옵션](https://sharp.pixelplumbing.com/api-output/#webp)

브라우저·Emulator·빌드·테스트를 중단한 독립 CPU 구간에서 전후를 순차 측정했다. 고정 synthetic JPEG, fixture별 warmup 3회와 측정 20회. 단위 ms, 순서 p50 / p75 / p95:

| 입력 | 변경 전 | 변경 후 | p75 감소 |
|---|---:|---:|---:|
| 1440×1080 | 410 / 419 / 429 | 389 / 390 / 391 | 7.0% |
| 2560×1920, orientation 6 | 1252 / 1272 / 1398 | 436 / 442 / 449 | 65.3% |

두 저장 variant의 SHA-256과 바이트 수는 전후 일치했다. 합계는 각각 617,430B와 468,384B다. 이 수치는 CPU 처리 실험이며 업로드 전송량 감소나 cloud 지연 감소를 의미하지 않는다.

재현: `scripts/benchmark-inventory-photo-server.ts`. 원시 표본·환경·source/fixture/output hash: ignored `output/inventory-performance/photo-server/{before,after}.json`.

## 클라이언트 사진 변환

Chromium CPU 4배 제한, 각 크기·방식별 warmup 3회와 측정 20회. 방식 순서를 회전하고 모든 결과의 바이트 일치를 확인했다. 1MiB 입력, 단위 ms, p50 / p75 / p95:

| 처리 | 기존 | 채택 방식 | 50ms 초과 작업이 겹친 표본 |
|---|---:|---:|---:|
| 상세 Base64 디코딩 | callback 342 / 351 / 363 | indexed loop 20 / 21 / 21 | 20/20 → 0/20 |
| 저장 Base64 인코딩 | spread+btoa 169 / 174 / 178 | FileReader 15 / 16 / 17 | 20/20 → 0/20 |

1.5MiB에서도 채택 방식의 p75는 디코딩 28.8ms, 인코딩 18.7ms였고 긴 작업은 없었다. Native Base64 API는 더 빨랐지만 오래된 브라우저용 분기를 추가하지 않아도 이번 측정의 50ms 기준을 만족해 도입하지 않았다. Worker나 촬영 직후 선행 준비도 추가하지 않았다. 저장 버튼을 누른 뒤 FileReader로 인코딩하고 기존 인증 Callable로 업로드한다. 이미지 품질과 실제 전송 바이트는 동일하다.

현재 디코딩은 binary string과 typed array를 만들며, FileReader는 data URL에서 Base64를 추출한다. 1MiB 실험의 JS heap 전후 차이 중앙값은 기존 callback 디코딩 40,739,644B, indexed loop 1,048,772B였다. 기존 인코딩은 8,907,084B였고 FileReader의 관측값은 348B였지만, 후자는 native/external buffer를 계수하지 못하므로 실제 메모리가 거의 필요 없다는 뜻이 아니다. 이 샘플은 GC를 포함한 최대 메모리나 총 복사량 측정도 아니다. 코드 변환 마이크로벤치 결과를 capture, upload, INP 결과로 해석하지 않는다. 재현: `scripts/benchmark-inventory-photo-client.mjs --run`; raw report: ignored `output/inventory-performance/photo-client/report.json`.

저장 클릭의 첫 paint가 기존 Base64 변환 때문에 항상 늦었다고 해석해서는 안 된다. 기존 코드도 비동기 파일 읽기 전에 busy 화면을 표시할 수 있었다. 동일한 원시 EventTiming을 재집계한 저장 클릭 p75는 100개 80→104ms·1,000개 88→64ms였다. 기존 약 600ms대의 click→busy 관찰값은 이후 동기 변환으로 자동화 관찰이 늦어진 영향도 포함한다. 사진 codec 변경은 post-click 준비 작업과 긴 작업 감소를 근거로 평가하며, 저장 첫 화면 반응 개선으로 주장하지 않는다.

## 브라우저 비교 및 회귀 검증

아래 지연·요청·바이트 수치는 `final-v3-source`와 `final-v3-built`에서 측정했다. 측정 뒤 최종 빌드 예산을 맞추기 위해 반복된 인증 오류 생성을 기존 접근 경계 모듈의 factory로 공유하고, 동시에 존재하지 않는 사진 성공·오류 상태를 단일 상태로 통합했다. 오류 분류의 중복 검사와 실사 날짜의 중복 변환도 제거했다. 실제 호출에서 항상 같은 값을 가진 사진 확대/확대 힌트 옵션은 하나로 합쳐 동일 화면을 유지했다. 내부 인증·사진 오류의 영문 진단 메시지를 짧게 통일했으며 인증 조건·거부 시점·오류 코드·사용자 메시지·비동기 순서는 유지했다. 최종 번들 크기는 별도 빌드 gate 결과로 기록한다. 따라서 측정에서 나타난 JS 수신량 +4,224B를 마지막 빌드의 정확한 증가량으로 해석하지 않는다.

### 동일 조건과 지표 해석

- 기준 source `082a6c0`와 최종 후보를 별도 source/export로 보존한다. Chromium 151.0.7922.34, 412×915, CPU 4배 제한, RTT 120ms, 다운로드 200,000B/s·업로드 100,000B/s다. 정상 비교는 Service Worker를 차단하고, 설치·제어된 SW 비교는 별도 수행한다.
- 사진이 많은 100개·1,000개 fixture 각각 미보고 warmup 1회 후 새 브라우저 context로 20회 측정한다. Emulator는 warm 상태다. 60초 snapshot의 실제 만료는 61초 대기로 확인한다. p50/p75/p95는 nearest-rank다.
- 검색 세 번, 서로 다른 상세 두 번과 목록 복귀, 유효 TTL 내 모드 재진입, 새 품목 진입을 반복한다. 각 fixture의 첫 5회에서는 사진을 포함한 등록을 두 번 수행해 저장 표본은 10개다.
- 파일 입력은 동일한 1600×1200 synthetic JPEG 1,361,107B를 로컬 경로로 전달한다. 실제 카메라·OS 선택 창 시간은 포함하지 않는다. SHA-256은 `693c07545bb070ae99b05a1ab969921e60acee440920cd1c848e94744bcf65dd`다.
- 여정 시간은 자동화 동작 시작→DOM 관찰로, Playwright 스크롤·actionability 대기가 포함된다. 실제 trusted click/마지막 keydown→관찰 DOM도 별도 기록한다. 후자도 polling을 포함하는 상한이며 paint 시간은 아니다. warm reentry의 원시 여정은 거래처 모드로 나갔다가 돌아오는 전체 동작이다.
- EventTiming의 interaction ID별 최대 지연으로 계산한 **실험실 INP 추정**을 사용한다. 충분한 실제 사용자 방문에서 수집한 field INP는 아니다. 입력 대기·처리·표시 지연, 50ms 초과 작업, 요청·바이트·chunk를 함께 기록한다. 사진 업로드 전송과 서버 처리 완료를 로컬 저장 표시와 분리한다.
- 측정 중 다른 빌드·테스트·CPU 벤치를 겹치지 않는다. demo 프로젝트의 합성 데이터만 사용하며 각 trial 사이 생성 fixture를 복원한다.

### 첫 페이지 40건 실험

**폐기하고 기본 100건을 유지한다.** 두 번째 페이지 응답을 보류한 1,000개 fixture에서 기존 100건 방식은 상품 0080을 검색할 수 있었지만 첫 40건 방식은 검색할 수 없었다. 응답을 풀면 두 방식 모두 찾았다. 초기 검색 completeness가 기존보다 나빠져 필수 조건을 실패했다. 따라서 40건의 p75 ≥20% 개선·전체 완료 p95 악화 ≤10% 수치 실험은 진행하지 않았으며 해당 속도 기준을 통과했다고 주장하지 않는다.

전체 로딩 후에는 기준 100건·후보 40건의 상품명 1개, 제조사 200개, 규격 1,000개, 원산지 1,000개, 유사 이름 prefix 99개, 초성 1,000개의 정확한 ID·개수가 일치했다. 메모와 product ID는 기존 검색 필드가 아니며 각각 0개 결과를 유지했다. 실제 최종 후보도 같은 progressive 검색과 8개 검색의 정확한 ID·개수 검증을 통과했다.

### 검색 프로파일에서 확인한 추가 병목

목록·상세 개선만 적용한 중간 버전의 1,000개 조건에서 검색 입력 처리 125.8ms가 관찰됐다. 별도의 실제 정적 빌드 화면에서 CPU 4배·V8 1ms 샘플링으로 세 검색어를 세 번씩 입력했다. 상위 self time은 문자열 정규화 3,971.6ms, 필드 연결·초성 검색 854.5ms, 등록일의 실사 대상 판단 894.9ms, 목록 행 793.8ms였다. 이 값은 프로파일 전체의 합계이며 한 번의 검색 latency가 아니다.

컴포넌트 내부 파생 데이터로 상품별 검색 문자열과 실사 집계를 재사용하도록 수정했다. 기존 네 검색 필드, 문장부호, 필드 연결, NFKC 전 초성 변환, 한국어 소문자 규칙을 유지한다. 같은 프로파일 조건에서 전체 sampled time은 10,251.7→4,213.1ms, 정규화는 3,971.6→약 14ms, 실사 대상 판단은 894.9→78.0ms였다. 행 렌더링은 793.8→818.1ms로 남았다. 이 프로파일 합계를 실제 입력 지연 개선율로 해석하지 않으며 최초 목록 준비 비용과 여정별 quantile은 최종 반복 측정에서 확인한다. 원본은 ignored `output/playwright/inventory-benchmark/core-search-profile/`, 변경 후는 `final-diagnostics/`의 `search.cpuprofile`과 `top-frames.json`에 각각 보존했다.

### 새 품목 진입 후보의 추가 진단

코드만 미리 import한 중간 후보는 클릭부터 입력 DOM 준비까지 p75를 100개에서 731.9→698.9ms, 1,000개에서 705.8→694.7ms로 줄이는 데 그쳤다(각 10회). 이미 준비된 컴포넌트를 처음부터 사용하는 후속 후보는 대기를 더 줄였지만, 첫 클릭 EventTiming이 약 432ms로 악화됐다. CPU 프로파일에서 native `showModal()` self time 약 296ms, trace에서 Layout 약 228ms와 UpdateLayoutTree 약 127ms가 관찰됐다. 이 후보는 그대로 채택하지 않는다.

동일 export의 진단용 ablation에서 닫기 버튼의 native autofocus 지정, backdrop blur 제거, 애니메이션 제거, 뒤의 목록 숨김·containment, 폼 grid 변경 모두 유효한 개선이 없었다. 폼의 `content-visibility` 후보도 실제 클릭 EventTiming을 악화시켜 제외했다. 포커스 정책·시각 효과·CSS 배치는 변경하지 않았다. 프로파일러와 trace를 끈 상태에서도 약 416ms가 관찰돼 계측 도구만의 비용은 아니었다.

마지막 진단에서 제목을 먼저 표시하고 다음 paint 뒤의 task에서 폼을 표시했을 때 제목은 약 88ms, 실제 보이고 활성화된 품목명 입력은 약 434ms, 클릭 EventTiming은 약 128ms였다. 전체 폼을 즉시 표시한 후보는 제목·입력 약 357ms, EventTiming 약 416ms였다. 즉시 응답을 개선하지만 이후 Layout 약 234ms는 남는다. 이를 재고 편집기 내부의 취소 가능한 mount gate로 구현했고 lifecycle 테스트와 최종 반복 비교로 검증했다. 숨은 활성 입력으로 준비 시간을 오인하지 않도록 준비 전에는 폼과 저장 버튼 자체를 mount하지 않는다. 이 진단은 반복 여정의 최종 p75가 아니며 최종 채택은 전체 비교로 판단한다.

초기 pilot은 selector·실험 도구 검증용이며 최종 before/after로 사용하지 않는다. 네트워크·CPU·사진 규격·상품 수·브라우저 조건을 고정하고, 실제 입력 이벤트와 자동화 여정 시간을 별도로 기록한다.

측정 버전의 재고 focused 472개가 통과했고, 이후 용량 정리의 관련 테스트를 다시 통과했다. 최종 전체 단위 테스트는 1,661개 통과·14개 조건부 skip이며 앱·Functions typecheck와 전체 lint도 통과했다.
