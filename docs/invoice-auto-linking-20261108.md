# 등록 상호·주소 표기 차이의 자동 연결

2026-11-08. 사용자는 인식된 상호가 맞아도 등록 표기 차이 때문에 매번 확인하는 불편을 줄이고, 같은 거래처는 자동 연결하며 실제로 애매한 경우만 확인하도록 요청했다. 로컬 구현·검증 완료 상태이며 이번 자동 연결 확대는 아직 운영 배포하지 않았다.

## 기존 원인과 변경

- 명세서 연결이 등록 이름 전체 또는 명세서의 괄호를 뺀 이름만 비교해 복수 등록 상호·법인 표기·등록 지점명이 있는 거래처를 놓쳤다. 명세서와 손글씨 목록 모두 등록 상호를 괄호 밖의 쉼표/세미콜론 단위로 비교하고, 법인 표기와 명시적인 운영 메모만 정리한다. 괄호 속 지역/지점은 보존한다.
- 주소의 정규식이 `진잠로 140번길 64`를 `진잠로 140`으로 잘못 분리했다. 도로명 전체와 건물/지번 번호를 비교하고 광역시 표기·공백·전각 문자 차이를 정리한다. 다른 번길·본번/부번·산 지번·시군구/읍면 차이는 그대로 구분한다.
- `동해냉동`처럼 여러 등록 항목에 들어 있는 상호는 후보 전체의 주소로 지점을 구분한다. 한 곳만 일치하고 다른 후보들이 다른 주소로 확인되는 경우 자동 연결한다. 주소가 빠져 확인할 수 없는 후보나 중복 후보가 있으면 확인을 유지한다.
- 문자열로 확인되지 않는 경우에만 기존 Kakao REST API로 등록 주소의 도로명·지번을 함께 조회한다. 유일한 정확 검색 결과만 증거로 사용하며, 좌표가 가깝다는 이유로 연결하지 않는다. 등록 주소에서 확인한 지번이 명세서 지번과 일치하면 짧은 명세서 주소의 전국 검색 첫 결과를 선택할 필요가 없다. [주소 검색 공식 응답 설명](https://developers.kakao.com/docs/ko/local/dev-guide#address-coord)
- 한 글자 도로명 오독은 제한적으로 처리한다. 등록 상호가 유일하게 정확히 일치하고, 도로명의 한글 한 글자만 다르며, 시군구·건물번호·사진의 괄호 안 동명이 모두 일치해야 한다. 추가로 원문 주소 검색이 명확히 0건이어야 한다. 실제 다른 주소가 검색되거나 검색 실패/복수 결과, 숫자·도로명 끝자리 변경, 지점명 추론이 필요하면 자동 보정하지 않는다. 사진과 등록 주소를 수정하거나 오독 표기를 별칭으로 학습하지 않는다.
- 직원이 확인해 기억한 줄임말도 동일한 도로명/지번 대조를 사용할 수 있다. 기존 별칭 키·직원 격리·수정/해제·revision 검증은 유지한다. 비슷한 상호나 새 줄임말을 임의로 자동 연결하지 않는다.

## 서버 계약과 처리 시간

- 추가 OpenAI 요청 없음. Sol/Luna와 명세서 공급자 차단 구조는 이전 배포 그대로다. 주소 검색에는 주소 문자열만 보내며 사진·상호·직원 정보를 보내지 않는다.
- 주소 검색과 정규화는 서버 RAM에서 처리한다. 조회 결과는 메모리에 정상 주소 24시간, 0건 5분 동안만 캐시한다. 한 번의 분석에서 최대 24개 주소, 동시 4개, 새 조회 시작 예산 8초, 각 실제 HTTP 요청 2초 한도를 둔다. 검색 실패는 해당 항목 확인으로 끝내며 다른 정상 항목의 등록을 막지 않는다.
- 외부 검색은 Firestore 트랜잭션 밖에서 수행한다. 최종 저장 시 권한·날짜·최신 거래처 목록/별칭을 다시 확인하고, 거래처 이름·주소·revision 등이 바뀌면 이전 검색 증거를 사용하지 않는다.
- `analyzeDeliveryInvoice`, `analyzeDeliveryPhotoBatch`가 기존 `KAKAO_REST_API_KEY` Secret을 함께 사용하도록 선언했다. 새 키 발급·키 변경·운영 IAM 변경은 하지 않았다. 로컬 코드 선언과 실제 운영 Secret 연결은 구분한다.
- 기존 Callable/App Check·request ID·감사 이력·목록 병합·중복 방지·서버 확인 후 완료·사진 Firebase 미저장 계약을 유지한다. UI 및 응답 스키마 변경은 없다.

## 실제 사진에 대한 비교

앞서 실제 OpenAI API로 인식한 사진 5장 × 3회의 결과 15개를 그대로 재사용했다. 현재 운영 거래처 223개를 읽기 전용으로 다시 조회하고, 새 연결 코드를 실제 Kakao API 응답과 함께 실행했다. OCR 코드는 이번 수정에서 바뀌지 않았으므로 OpenAI를 다시 호출하지 않았다.

| 인식된 상호 | 기존 연결 / 새 연결 (날짜 일치 조건) | 판단 근거 |
|---|---|---|
| 동해냉동 | 0/3 → 3/3 | 다른 구의 복수 상호 항목과 목상동 지점 주소 구분 |
| 푸드원 | 0/3 → 3/3 | 등록 복수 상호와 용산2로의 지번 용산동 638 일치 |
| 자연푸드 | 0/3 → 3/3 | 법인 표기 정리·등록 복수 상호와 갑동로 주소 일치 |
| 디에이치푸드 | 0/3 → 3/3 | 진잠로140번길 공백 차이 정리 |
| 찬솔유통 | 0/3 → 3/3 | 법인/운영 메모 정리, 한 글자 주소 오독의 독립 근거 대조 |

- 올바른 자동 연결 15/15, 잘못된 연결 0. 이 다섯 사진의 결과이며 전체 거래처에 대한 일반 인식률은 아니다.
- 이 사진들은 모두 11/9 명세서다. 비교에서 11/9를 납품일로 둔 경우 위 결과가 나왔고, 실제 시험일 11/8을 적용하면 기존 날짜 확인을 유지해 15개 모두 자동 저장하지 않았다. 날짜가 다른 명세서를 임의로 오늘 납품으로 바꾸지 않는다.
- 새 연결 단계만 측정한 첫 실행은 사진별 약 12~86ms, 서버 RAM 캐시 사용 후 약 11~16ms였다. 첫 5장 전체에 실제 주소 요청 3회, 뒤의 10개는 캐시 재사용이었다. 이는 로컬에서 연결 계산과 주소 API를 측정한 값으로, 전체 OCR·업로드·서버 기동·Firestore 지연은 포함하지 않는다.
- 운영 데이터 시험 쓰기와 사진 업로드 없음. 실제 API 응답·원본·거래처 사본·비교 결과는 Git 제외 `output/invoice-linking/`에만 보관한다.

## 검증

- 전체 Functions 단위 735개 통과, 기존 조건부 16개 생략. 이후 손글씨의 법인/복수 상호 검사 1개를 추가한 파일 17개 검사 통과: 관련 전체 검사 총 736개.
- 기존 사진 일괄 서비스 에뮬레이터 22개 통과.
- 새 연결 서비스 에뮬레이터 8개 통과: 기존 목록 보존·중복 재요청, 단일 명세서 호환, 조회 중 거래처 변경·신규 동명 추가·권한 취소 차단, 주소 서비스 실패 시 부분 정상 등록, 날짜 확인 유지, 기억한 줄임말의 지번/도로명 자동 연결과 별칭 중복 생성 방지.
- 실제 인식 응답 15개를 두 날짜로 재생한 등록 시나리오 30개 통과. 납품일 일치 시 자동 등록과 request ID 재요청, 날짜 차이 시 수동 확인 후 저장, 사진/공급자 증거 미저장 검증.
- Functions TypeScript build, 변경 파일 ESLint, diff 검사 통과. UI 변경이 없어 Hosting build/브라우저 검사는 반복하지 않았다.
- 운영 배포 전 단계다. 배포 대상은 최소 `analyzeDeliveryInvoice`, `analyzeDeliveryPhotoBatch`이고, 줄임말 저장 충돌 검사도 정규화가 개선되어 함께 반영하려면 `confirmDeliveryPhotoBatch`를 포함한다. 이후 운영 반영 시 승인 범위와 서버/데이터 보존 증거를 기록한다.
