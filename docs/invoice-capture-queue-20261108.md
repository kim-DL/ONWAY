## 문제와 변경

이전 화면은 사진 분석과 촬영 버튼이 같은 busy 상태에 묶여 있었다. `addFiles`도 처리 중 추가 입력을 거부하고, 최초 선택한 고정 배열만 처리했다. 따라서 다음 명세서를 촬영하려면 앞 사진의 분석 응답을 기다려야 했다.

분석 작업과 확인 저장/경로 계산의 잠금을 분리했다. 분석 중 카메라와 갤러리는 계속 열 수 있으며, 새로 촬영한 파일 ID를 메모리 대기열에 추가한다. 단일 작업자가 처리 중 추가된 항목까지 순서대로 가져간다. 분석/저장 네트워크 요청을 병렬화하지 않아 기존 서버 목록 revision 및 비용 제한 계약을 유지한다.

- 첫 사진 선택 후 고정 하단에 ‘다음 촬영’ 버튼 표시. 사진 처리 중에도 사용할 수 있다.
- 대기 수와 진행률을 표시하고 각 항목을 대기·분석 중·저장됨·확인 필요·재확인으로 구분한다.
- 한 장의 실패는 이후 사진 처리를 멈추지 않는다. 재시도는 기존 request ID를 재사용한다.
- 기존 한 번 20장·화면당 60장·파일당 20MB 제한을 유지하며, 처리 중 연속 입력에도 동기 ref로 누적 수를 확인한다.
- 파일과 대기열은 화면 메모리에만 둔다. 완료된 파일을 해제하고 unmount 시 남은 파일/대기열을 비운다. 실행 중 네트워크 요청이 이미 서버에 도달했다면 서버 처리는 완료될 수 있다.
- 처리 중 일반 닫기·완료·경로 계산은 잠그고, 처리/실패/검토가 남은 경우 beforeunload 경고를 요청한다. 브라우저·OS 강제 종료에서 보관/복구를 보장하지 않으며 새로운 영구 저장소는 사용하지 않는다.

## 최종 검증과 배포

사용자가 실제 첨부 명세서 시험과 배포를 명시적으로 요청했다. 기존 연속 촬영 브라우저 22개를 다시 실행해 모두 통과했고, 관련 서버 단위 35개와 에뮬레이터 19개, 타입·관련 lint·운영 build/PWA/Hosting/성능 gate도 통과했다. 단위 검사 첫 명령은 Vitest 필터에 wildcard를 전달해 테스트를 찾지 못했으며, 디렉터리/이름 필터를 바로잡은 최종 실행에서 3개 파일 35개가 통과했다.

실제 첨부 JPEG를 운영과 같은 `invoiceImage` 및 `createPlanningProviders.readInvoice`에 전달해 OpenAI Responses API를 호출했다. 모델은 `gpt-6-luna`, `store:false`. 이미지 서버 전처리부터 API 응답까지 **5,096ms**였으며, 휴대폰 업로드·Callable 인증·Firestore 저장을 포함한 전체 소요 시간은 아니다. 공급받는 자 상호와 괄호 지역명을 정확히 읽고 실제 운영 거래처를 읽기 전용으로 조회해 상호·주소가 맞는 기존 거래처 한 곳에 연결했다. 고객 식별자와 주소, 사진 원본/인식 내용은 이 문서에 남기지 않는다.

명세서 거래일자는 **2026-11-09**, 테스트 당일은 **2026-11-08**이므로 실제 당일 자동 등록은 차단되고 확인 대상으로 분류되는 것이 정상이다. 실제 API에서 받은 필드와 해당 거래처의 최소 비교 정보를 로컬 에뮬레이터에 연결해 아래를 확인했다. 운영 납품 목록에 시험 기록을 만들지 않았다.

- 날짜가 다르면 확인 전에는 내 납품처·오늘 납품처를 생성하지 않음. 날짜 확인 후 양쪽 목록에 저장.
- 에뮬레이터 시계만 명세서 날짜로 설정하면 같은 사진·인식 결과로 두 목록 자동 등록. 원본 사진과 인식 날짜는 변경하지 않음.
- 동일 request ID 재시도 시 인식 제공자 재호출 없음. 다른 request ID로 같은 거래처를 재등록해도 두 목록과 revision이 그대로 유지됨.
- 거래처 원본 데이터 유지, 처리 영수증에 이미지/base64 미저장.

실제 OpenAI 호출은 인식·매칭 검증이며, 등록 검증은 그 응답을 재사용한 격리 에뮬레이터 시험이다. 인증된 운영 Callable 또는 실물 휴대폰 카메라 전체 흐름을 실행한 것으로 해석하면 안 된다.

`firebase deploy --project onnuriway --only hosting:onnuriway --non-interactive`로 Hosting만 배포했다. 두 운영 주소에서 공개 응답 검사 각각 34개 및 JS/CSS 각각 99개 해시 일치를 확인했다. 후보 129개 파일 일치, 서버 78개 미변경. 배포 전후 상품 92개·lot 89개·입출고 240개 문서 해시가 동일하다. 이미지 Firebase 보관 정책과 기존 재고·입출고 기록을 변경하지 않았다.

검증 근거는 gitignored `output/invoice-queue-release/`의 API 결과, 에뮬레이터 결과, 배포 상태·인벤토리 해시·공개 응답 검증에 있다. 실제 인식 필드가 담긴 로컬 파일은 커밋하지 않는다.
