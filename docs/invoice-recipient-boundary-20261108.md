# 공급자와 공급받는 자 인식 분리

2026-11-08. 사용자 운영 화면에서 공급자 온누리종합식품과 회사 주소가 명세서 거래처 확인 항목으로 표시되는 오류를 제보받았다. 사용자가 복원한 실제 명세서 5장의 시험과 문제 없을 때 운영 배포를 승인했다. 아래 최종 소스를 두 인식 서버에 반영할 준비를 마쳤으며, 배포 결과는 별도로 기록한다.

## 원인과 변경

기존 일괄 인식은 Sol의 일반 사진 추출 결과가 명세서이면 Luna를 다시 호출했지만, 두 호출 모두 같은 `rawName/address` 형식과 일반 문서 지시를 사용했다. 최종 결과에 공급자/수취인 구역을 구분할 근거가 없었고 서버에서도 공급자 오인 결과를 거부하지 않아 잘못된 이름을 확인 후보로 표시할 수 있었다. 같은 원본을 기존 운영 구현으로 재시험한 결과, 찬솔유통에서 첫 Sol 응답은 수취인을 읽었지만 최종 Luna 응답은 온누리종합식품과 공급자 주소를 선택했다. 동해냉동은 최종 응답에서 동해생동으로 오독했다.

- 명세서 두 번째 호출을 전용 `delivery_invoice_parties` 형식으로 변경했다. 공급자와 공급받는 자의 상호·주소·사업자번호를 각각 읽고, 수취인이 `공급받는자` 구역에서 나온 것인지 함께 확인한다.
- 표의 같은 구역에서 상호·주소·사업자번호를 읽도록 명시했다. 좌우 위치만으로 판단하지 않고 세로/띄어쓰기 라벨을 읽는다. 성명·품목 비고의 학교명·공급자는 수취인으로 쓰지 않는다.
- 최종 거래처 결과는 서버가 수취인 필드에서만 만든다. 공급자 상호/사업자번호와 같거나 자사 공급자 정보이거나 구역이 불명확하면 인식 실패로 처리한다. 해당 응답을 수동 연결 후보로 노출하거나 첫 모델 결과로 대체하지 않는다.
- 여러 명세서 중 하나가 공급자를 수취인으로 반환해도 사진 전체를 부분 저장하지 않는다. 공급자 증거 필드는 내부 검증 후 버리며 저장 결과/거래처 후보로 전달하지 않는다.
- 단일 명세서 API도 같은 수취인 검증을 사용하고 기존 반환 형식을 유지한다. 여러 명세서가 오면 거부하고 연도 없는 날짜는 임의로 채우지 않는다.
- 세로형 단일 명세서는 전체 사진과 상단 절반 확대본을 같은 Luna 요청에 함께 전달한다. 작은 글자를 재확인하며 별도 명세서로 세지 않도록 명시한다. 여러 명세서 사진에는 단일 상단 확대를 적용하지 않는다. 확대본도 메모리에서만 만들고 저장하지 않는다.
- 기본 Sol→Luna 호출 수는 기존과 같은 2회다. 손글씨 목록은 기존 Sol 1회로 유지한다. 두 설정을 같은 모델로 바꾼 특수 구성에서도 명세서 전용 검증은 생략하지 않는다.
- UI·Firestore 데이터·권한·App Check·request ID·revision·별칭 저장 정책·등록 사진 미저장 계약은 변경하지 않았다. 기존에 만들어진 확인 항목이나 이미 등록한 운영 기록을 소급 수정하지 않는다.

## 확인 결과

- 관련 단위 92개 통과: 공급자/수취인 분리, 자사 공급자·동일 사업자번호·역할 불명·빈 수취인 거부, 일부 잘못된 복수 명세서 거부, 첫 응답으로의 fallback 금지, 손글씨 단일 호출 유지.
- 사진 일괄 서비스 에뮬레이터 22개 통과. 정상 수취인만 자동 저장하는 경로와 공급자 오인 시 목록·별칭·확정 가능한 결과가 만들어지지 않는 경로를 추가했다.
- Functions build, 변경 파일 ESLint, diff 공백 검사 통과.
- 기존 소은푸드 명세서 실제 OpenAI API 1회: `소은푸드 (금산)`과 수취인 주소 추출, Sol→Luna 2호출, 6.246초.
- 기존 손글씨 사진 실제 API 1회: customer_list 12줄 유지, Sol 1호출, 4.285초.
- 위 시간은 각 1회 로컬→API→로컬 결과이며 평균·일반 성능이나 휴대폰 전체 처리 시간으로 해석하지 않는다. 운영 데이터 시험 쓰기 없음.

## 복원된 원본 5장 실제 API 시험

원본을 Git 제외 `output/invoice-recipient-fix/images/`에 확보하고, 실제 앱의 브라우저 JPEG 전처리와 서버 전처리를 동일하게 적용했다. 운영 거래처 223개는 읽기 전용으로 조회했다. API 키는 기존 Firebase CLI 인증으로 Secret Manager에서 메모리에만 읽었으며 변경하지 않았다.

| 공급받는 자 | 기존 방식 1회 | 최종 방식 3회 |
|---|---|---|
| 동해냉동 | 동해생동 오독 | 3/3 정확 |
| 푸드원 | 정확 | 3/3 정확 |
| 자연푸드 | 정확 | 3/3 정확 |
| 디에이치푸드 | 정확 | 3/3 정확 |
| 찬솔유통 | 공급자 온누리종합식품 선택 | 3/3 정확 |

- 공급받는 자 상호: 최종 15/15 정확, 공급자 노출 0/15. 회사 형태와 괄호 메모는 보존했다. 이 다섯 사진의 반복 시험 결과이며 일반적인 전체 인식률을 의미하지 않는다.
- 구역 분리만 한 중간안은 자연푸드를 3회 중 2회 지연푸드로 읽었다. 상단 확대본 추가 후 최종 3회는 모두 자연푸드였다. 실패 결과는 `after-before-closeup.json`에 보존했다.
- 최종 API 처리: 중앙값 5.854초, 평균 6.512초, 범위 4.478~12.538초. 기존 5회 중앙값 5.914초. 로컬→실제 API→결과 시간이며 휴대폰 업로드·Functions 기동·저장은 포함하지 않는다.
- 날짜는 모두 2026-11-09로 정확히 읽었다. 시험일 11/8의 오늘 목록 자동 등록은 기존 날짜 확인 절차로 막힌다.
- 주소는 공급받는 자 구역에서 읽었다. 찬솔유통의 최종 판독값 `학하북용로 96`은 등록 주소 `학하복용로 96`과 다르므로 정확한 주소 일치로 평가하지 않는다. 이름 15/15와 주소 정확도는 구분한다.
- 이번 5장은 당일로 가정해도 기존의 보수적 연결 규칙상 모두 확인 대상이다. 복수 등록 상호·괄호 상호, 지번/도로명 차이, 주소 띄어쓰기 및 판독 차이가 남아 있다. 이 수정에서 연결 규칙을 완화하거나 운영 주소를 수정하지 않았다. **상호 인식 성공을 자동 연결 성공으로 보고하지 않는다.**
- 실제 결과 15개를 현재 거래처 사본으로 에뮬레이터에 재생하고, 11/8과 11/9 각각 분석→확인→저장→같은 request ID 재요청 30개 시나리오가 통과했다. 날짜 확인 없이 저장 불가, 확인 후 선택한 수취인만 내 납품처/오늘 납품처에 저장, 중복·불필요한 별칭 생성·사진 데이터 저장 없음이 검사 결과다.
- 시험 사진과 실제 모델 원문은 Git 제외 로컬 폴더에만 보관한다. Firebase Storage 업로드와 운영 데이터 시험 쓰기는 하지 않았다.

## 배포 범위

사용자가 승인한 대상은 인식 서버 두 개(`analyzeDeliveryPhotoBatch`, `analyzeDeliveryInvoice`)다. UI와 Hosting 재배포는 필요하지 않다. 배포 전후 서버 82개 및 상품·lot·입출고·거래처·납품사진·내 납품처·오늘 납품처 문서 해시를 비교한다. 배포 완료 여부와 revision은 아래 후속 기록에서 확인한다.
