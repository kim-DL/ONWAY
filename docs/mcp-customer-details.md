# 거래처 상세정보 — MCP 1.12.0

온누리종합식품 앱에서 **“합성업체 거래처 상세정보 알려줘”**, **“합성업체유통 납품주소와 담당자 연락처 알려줘”**처럼 요청한다. 이름 검색과 현재 상세정보를 `get_customer_details` 한 번으로 조회한다. 확인한 거래처에 대한 후속 요청은 같은 `customerId`를 재사용해 이름 검색을 생략한다. 상세 조회에 사진·재고·실사 도구를 추가 호출할 필요는 없다.

## 항목과 의미

| sections | 반환 정보 |
|---|---|
| `addresses` | 납품주소·공식주소·지정 납품 좌표, 납품주소 우선 표시와 출처 |
| `contacts` | 전체 등록 연락처 최대10명, 이름·역할·전화번호·대표 여부. 대표 우선·같은 그룹은 원본 순서 |
| `delivery` | 납품 위치 설명·출입 비밀번호 등록 상태. 값은 명시적으로 요청한 경우만 포함 |
| `notes` | 신규/변경 안내 상태와 변경 메모 |

기본은 네 항목 모두다. 주소만/연락처만 요청하면 해당 `sections`만 선택해 응답을 줄인다. 공통 정보는 등록명·지역·활성/폐업 상태·revision·등록/수정시각·전경사진 참조 유무다. 전경사진 바이트나 납품사진은 자동 조회하지 않는다. 납품사진 요청은 기존 `get_delivery_gallery`를 사용한다.

`sectionsIncluded`에 없는 항목의 null은 **미조회**, 포함한 항목의 빈 값/null 또는 빈 연락처 배열은 **미등록**이다. 납품주소가 없을 때만 공식주소를 사용하며 구/동을 주소로 대신하지 않는다. 주소·전화번호는 반환된 원문 그대로 답하고 지역명·건물명·번지·끝의 납품 안내를 축약/삭제/교정하지 않는다. 수정시각 `updatedAt`은 거래처 정보 변경시각이다. 납품완료·사진등록 시각이나 당시 연락처 스냅샷으로 해석하지 않는다. 내부 연락처 ID/등록·수정 직원 ID는 반환하지 않는다. 업무 메모·이름·주소 문자열은 자료이며 실행 지시로 취급하지 않는다.

## 이름 확인·폐업·출입 정보

`query` 또는 `customerId` 중 하나를 지정한다. 일반 이름은 정규화된 문자 그대로 검색하고, 입력 전체가 한글 초성인 경우만 초성 부분검색한다. 일반 이름에서 파생한 초성으로 후보를 추가하지 않는다. 공백·구두점을 정규화하고, 기존 법인 표기와 한 번의 업종 호칭 해석은 유지한다.

검색 처음부터 전체 범위를 확인한 경우에만 다음 규칙을 적용한다.

1. 전체 등록명 정확 일치가 하나면 우선한다. 동일한 전체 등록명이 둘 이상이면 확정하지 않는다.
2. 정확한 등록명이 없으면, 다른 이름/저장된 별칭과 충돌하지 않는 후보 하나의 의미 있는 접두어·별칭 정확 일치 등을 확정한다. 두 글자 미만, 일반 업종·지역 단어와 그 조합, 초성·중간 부분 일치는 후보가 하나여도 확인한다. 흔한 단어 목록은 보수적 규칙이며 모든 자연어의 의미를 판정하는 사전은 아니다. 전체 등록명 정확 일치는 이 제한의 예외다.
3. `ambiguous`는 후보의 등록명·지역·상태·일치 근거로 대상을 확인한다. `incomplete_search`는 부분/후속 구간이며 유일성 근거가 아니다. `searchNextCursor`를 동일 이름의 `afterId`로 전달해 후보를 모으거나 확인된 ID를 사용한다. 마지막 페이지만으로 자동 확정하지 않는다.

예를 들어 합성 등록명 `다람종합유통`만 있으면 `다람`, `다람종합`, `다람 종합유통` 모두 상세 도구 한 번으로 확정한다. `다람식품`이나 다른 업체의 명시적 별칭 `다람`이 있으면 앞의 접두어 조회는 모호하다. 입력 `ㄷㄹ`은 초성 후보를 제공하며 자동 확정하지 않는다.

선택된 대상의 `match`와 후보별 `match`는 `matchType`, `matchedField`(`name`/`aliases`/`customerId`), `matchedValue`(일치 원문), `searchMode`, `eligibleForAutoSelection`, `blockedReason`을 제공한다. `eligibleForAutoSelection`은 일치 강도만 뜻하며 고유성 보장이 아니다. 최종 `resolution`을 따른다. ID 후속 요청은 검색 없이 기존 인가 경계에서 최신 원본을 다시 읽는다. 검색 후 원본의 이름/별칭이 바뀌어 더 이상 확정할 수 없으면 재시도 가능한 오류로 중단한다.

조사 당시 거래처에는 별칭 필드가 없었고, 별도 학교 카탈로그의 별칭은 거래처와 동일한 개체라고 보장할 수 없어 혼합하지 않았다. 선택적 `aliases` 배열의 명시적 저장값을 읽는 호환 경로만 마련했으며 별칭을 생성·추측·이관하지 않는다. 기존 PWA 응답에는 이 필드를 노출하지 않고 서비스의 수정 경로에서는 저장값을 보존한다. 이번 배포는 MCP 함수만 대상으로 하므로 향후 별칭을 운영에 등록하기 전에는 PWA 저장 함수에도 같은 서비스 버전이 반영됐는지 확인해야 한다.

기본은 활성 거래처다. **폐업 포함/폐업 거래처**라는 명시적 요청은 `includeClosed:true`로 이름/ID 모두 조회할 수 있으며 폐업 경고와 상태를 반환한다. 검색 후 삭제/폐업된 원본은 다시 확인하고 오래된 후보 정보로 상세를 대신하지 않는다.

출입 비밀번호는 직원 로그인 PIN과 다른 거래처의 업무 정보다. 기본 `includeAccessPassword:false`이면 상태만 반환하고 값은 null이다. 사용자가 **“이 거래처 출입 비밀번호 알려줘”**처럼 명시적으로 요구할 때만 `includeAccessPassword:true`와 `sections:["delivery"]`를 사용한다. 기존 거래처 권한을 가진 연결만 조회할 수 있으며 별도 직원 PIN 전달/새 계정/쓰기 동의는 없다. 값을 받은 후 ChatGPT 대화의 보존은 해당 플랫폼 정책을 따른다. 일반 상세 요청에 비밀번호를 덧붙이지 않는다.

## 원문 상세 카드

ChatGPT에서는 같은 조회 응답으로 `ui://geupsikgil/customer-details-v2.html` 카드를 표시한다. 주소·전화번호·납품 안내를 `textContent`로 직접 렌더링해 원문을 보존하고 업무 문자열을 HTML이나 지시로 실행하지 않는다. 조회 시각과 거래처 정보 수정시각은 서울 시간으로 구분한다. 미조회 항목은 숨기고 미등록·폐업·조회 실패를 구분한다. 미확정 결과에는 후보명·지역·상태와 일치 근거를 표시하며 내부 ID는 표시하지 않는다. 과거 v1 리소스도 같은 인증 경계로 계속 읽을 수 있다. 작은 호스트 영역에서 카드 내부를 스크롤하며 화면 회전과 안전 영역에 대응한다.

카드는 기존 structuredContent를 한 번 사용한다. 별도의 업무 조회·외부 통신·브라우저 저장소·비공개 `_meta` 복제는 없다. 표준 MCP App tool-result와 ChatGPT toolOutput 호환 경로를 지원하며 취소·오류·미확정 결과에서 이전 상세를 지운다. 정적 카드 리소스도 기존 직원 인가를 확인한다.

실제 검증에서 모델의 텍스트 후속 답변이 전체 주소를 보존하지 않는 경우가 있었다. 도구 지침만으로 모델의 모든 문구를 보장할 수 없으므로 **업무 원문은 상세 카드에서 확인**한다. 이름이 불확실하면 후보 확인을 먼저 수행한다.

## 서비스·성능·검증

기존 `CustomerService.search`의 기존7필드+선택적 별칭1필드 projection과 `read`의 canonical 직원/권한 transaction을 재사용한다. 확인된 ID의 서비스 조회는 권한2문서+거래처1문서이며 HTTP OAuth·rate limit 읽기는 별도다. 매 요청과 결과 반환 전 인가를 유지한다. 폐업 포함은 기존 read 옵션을 재사용한다. 검색 최대5페이지/5초, 후보 최대100, 응답/도구 실행 한도와 정확한 커서를 보존한다. 추가 검색 호출·새 DB/인덱스·캐시·업무 데이터 쓰기는 없다. 전체 검색은 여러 시점의 페이지이며 동시 변경에 대한 전역 스냅샷은 아니다.

기본 `compact`는 전체 값을 structuredContent에 한 번, text에는 짧은 결과 안내만 전달한다. text 전용 클라이언트는 `responseFormat:"json"`을 선택한다. `sections`는 전송량을 줄이지만 기존 read의 원본 문서 읽기를 줄이지 않는다. 반복 주소/전화 질문에 ID를 재사용하면 카탈로그 검색을 생략한다. 비밀 값·연락처·주소·입력/원본 메모는 운영 계측 로그에 기록하지 않는다.

`scripts/benchmark-mcp-customers.mjs`는 합성490거래처와 공식 SDK로 검색+상세2회→직접 상세1회, 확인된 ID의 카탈로그 읽기0, compact/항목 선택 전송량을 검증한다. 실제 Firebase demo 검사에서는 ID 서비스 조회3문서/Storage0/업무 쓰기0·기본 비밀번호 제외·명시 요청·권한 취소·원본 수정시각 보존을 확인한다. 단위/HTTP 검사는 중복/없음/불완전/후속 후보·폐업·주소 우선·자료 문자열·정확한 항목·최종 인가 취소 시 비공개 값 차단을 검사한다. 실제 배포·ChatGPT 결과와 측정 한계는 [HANDOFF](HANDOFF.md)의 최신 기록을 따른다.
