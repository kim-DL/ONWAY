# MCP 1.7 재고 조회·승인 저장

기존 급식길 직원 PIN 계정을 사용한다. 별도 업무 DB·계정·재고 계산 로직을 만들지 않는다. 운영 배포/실제 ChatGPT 검증 결과는 [HANDOFF](HANDOFF.md)의 최신 항목을 따른다.

## 정확한 의미

| 정보 | 기준 |
|---|---|
| `lastStocktakeAt` / `lastStocktake` | 해당 제품의 마지막 `count_match` 수량일치 버튼 원본. 다른 창고 완료 여부와 무관 |
| 기록자 | 원본 `actorEmployeeId`에 연결한 **현재** 직원 명부 이름. 누락은 null이며 로그인 사용자로 추측하지 않음 |
| `updatedAt` | 상품 문서 수정 시각. 실사일/정확한 마지막 수량 변경일이 아님 |
| 이력 `registeredAt` | 원본 재고 이벤트 저장 시각. 실측을 시작한 시간이나 납품완료 시각이 아님 |
| `counts.stocktakeByLocation` | 현재 실사 주기의 창고별 PWA 완료 상태. 실사일 입출고도 반영하므로 버튼 건수와 다름 |
| 유통기한 알림 | 재고가 남은 창고의 가장 빠른 날짜. 전체 수량이 그 날짜에 만료된다는 뜻이 아님. 정확한 묶음별 수량/날짜는 상세 조회 |

날짜 검색은 서울 00:00부터 종료일의 다음 00:00 직전까지다. `unknown`과 `not_applicable`을 임의의 날짜로 변환하지 않는다. 입출고/수량조정은 수량일치로 표시하지 않는다. 수량일치 승인에는 실제 재고 확인이 필요하다.

## 빠른 조회

- “오늘 수량일치 확인 이력 10건을 기록자·창고·시각과 함께 보여줘.”
- “김직원의 10월 1~9일 냉동1 수량일치 이력을 보여줘.”
- “이번 주 직원별·창고별 수량일치 건수만 요약해줘.”
- “이 상품의 어제부터 오늘까지 입출고·이동·조정 내역과 변경 전후 수량을 보여줘.”
- “현재 창고별 실사 완료·변동·미확인 현황을 요약해줘.”

`search_inventory_records`는 직원 이름/ID, 창고, 상품 ID, 최대93일 날짜 범위, 이벤트 종류를 AND로 검색한다. 기본 `kind=count_match`; `kind=all`은 전체 재고 변동 종류다. 등록시각 내림차순/같은 시각은 문서 경로 내림차순이다. 날짜·필터·조회 상한을 담은 커서를 동일 조건으로 이어간다. 수량 변경은 append-only 이벤트 기준이며 페이지 사이 상품/직원 이름은 변경될 수 있다.

`includeLines=true`는 전후 수량·묶음 유통기한을 포함한다. 직원·창고별 건수만 필요하면 `includeRecords=false`로 개별 행 및 상품 이름 조회를 생략한다. 이때 `records=null`이고 `recordsIncluded=false`이며 원본 이벤트 읽기는 생략하지 않는다. `summary`는 이번 페이지 수행 건수이고 직원의 담당 업무 완료율이 아니다. `distinctProducts`는 페이지 사이 중복될 수 있어 합산하면 전체 고유 상품 수가 되지 않는다. `page.complete=false`는 같은 조건으로 다음 페이지를 읽어야 한다. 이동의 장소 필터는 출발 창고이며 목적 창고는 `lines`에 있다. 비활성/삭제 제품의 기존 이력은 유지한다.

기존 `get_inventory_overview`에 창고별 상태를 추가하여 같은 상품 순회 안에서 집계한다. 상품 검색의 Firestore 필드 projection은 최대200묶음의 내부 `inspectionByLot`을 제외한다. 기존 PWA 목록·재고 최신성·직원 재인가는 유지한다. 재고/권한 캐시는 없다. 인덱스8개는 원본 `events` COLLECTION_GROUP의 kind + 직원/상품/장소 조합 + createdAt DESC/name DESC이며 기존 인덱스와 별도로 추가한다. 원본 문서 backfill은 필요 없다. 인덱스 저장 및 이후 이벤트 쓰기 인덱싱 비용은 추가된다.

## 승인 저장

지원 범위는 수량일치, 실사 수량 조정, 입고, 출고, 수량 설정, 창고 이동, 묶음 이름/유통기한 수정이다. 상품 삭제·상품 등록·거래처 수정·관리자 설정 변경은 이 릴리스의 쓰기 범위에 포함하지 않는다.

1. 실제 변경 요청은 `requireWriteAccess=true`로 쓰기 동의부터 확인한다. 조회 권한으로 단순 미리보기만 확인하려면 false(기본값)를 사용한다. 자연어로 변경을 요청하면 `preview_inventory_change`가 현재 자료로 변경 전후를 계산한다. 업무 데이터는 아직 변경하지 않는다.
2. 카드에서 상품·창고·기본 단위·전후 수량·유통기한·사유를 확인한다. 수량일치는 실제 수량을 확인했다는 체크가 필요하다.
3. 사용자가 **승인하고 저장**을 누르면 UI 전용 `commit_inventory_change`가 기존 `InventoryService`를 호출한다. 완료 응답이 와야 저장 완료다.

예: “이 상품 냉동1에서 3봉 출고하는 미리보기를 만들어줘.”, “이 묶음 5봉을 냉동2로 옮기고 싶어.”, “실제로 확인했어. 이 상품 냉동1 수량일치 확인을 준비해줘.” 수량은 기본 낱개 단위다. 여러 유통기한 묶음 중 어떤 묶음인지 불명확하면 먼저 선택해야 하며 자동으로 수량을 배분하지 않는다. 새 입고 묶음은 유통기한 상태를 지정해야 한다. 같은 원본 묶음의 유통기한 수정은 이동한 모든 창고에 적용되므로 카드에 함께 표시한다.

## 인증·동시 변경·재시도

- 조회 scope `geupsikgil:read`는 유지한다. 저장은 **`geupsikgil:read geupsikgil:inventory.write`**에 기존 PIN으로 별도 동의해야 한다. 기존 read 토큰/refresh는 자동 승격되지 않는다. viewer는 쓰기 동의를 발급받지 못한다. delivery/sales 역할도 현재 canonical 권한을 매번 검증한다.
- 기존 연결은 조회/미리보기를 계속 사용할 수 있다. 쓰기 scope challenge 후 재연결/추가 동의가 필요하며 새 연결에서는 새 미리보기를 만든다. PIN은 급식길 HTTPS 인증 화면에만 입력한다. 대화/클라이언트 설정에 입력하지 않는다.
- PIN 제출 중에는 연결 버튼을 잠가 중복 제출을 막는다. 인증 화면은10분/일회용이므로 만료·이미 처리 안내가 나오면 새로고침으로 재전송하지 않고 ChatGPT에서 연결 상태를 확인한 뒤 다시 연결한다. 다른 앱으로 새 등록한 연결은 기존 앱의 쓰기 동의를 자동으로 공유하지 않는다.
- ChatGPT의 비공개 도구 연결 검증을 위해 저장 도구에도 표준 `ui.resourceUri`와 호환 `openai/outputTemplate`을 함께 제공한다. 앱 아이콘은 기존 로고를 MCP Hosting의 `/onnuri-icon-v1.png`로 제공하며 서버 초기화 `icons`와 PIN 화면에서도 사용한다. 플러그인 패키지의 listing/composer 로고와 MCP 서버 아이콘은 서로 다른 메타데이터다.
- ChatGPT 맞춤형 MCP 등록 화면의 앱 사진은 별도로 업로드한다. 2026-10-09 확인 기준 PNG 최대10KB/권장256×256이다. 업로드용 `assets/brand/onnuri-mcp-app-icon-256.png`는256×256/7,460B이며 기존 로고의 형태를 유지한다. 원본1254PNG는 용량 제한을 초과한다. 서버 `icons`나 플러그인 ZIP 로고만 수정해도 기존 앱의 저장된 사진이 갱신되는 것은 아니다. 새 연결 등록 후 플러그인 상세와 앱 설정 양쪽에서 실제 로고 표시를 확인했다.
- 미리보기는5분간 유효하다. 승인 capability는 `_meta`로 UI에만 전달하고 모델-visible text/structuredContent에는 넣지 않는다. 실행 도구는 `ui.visibility=[app]`이며 모델을 대신한 자동 저장 경로를 제공하지 않는다. 이 경계는 MCP 호스트가 UI metadata와 모델 가시성을 준수한다는 신뢰를 전제로 한다. 직접 만든 다른 인증 클라이언트도 사용자 확인 절차를 지켜야 한다.
- capability는 직원 UID/세션/권한 버전/역할, OAuth family, 정확한 명령에 묶인다. 서버에는 해시만 저장한다. 같은 family의 정상 refresh는 사용할 수 있으나 다른 연결/다른 직원/변조 토큰은 거부한다. 원래 명령은 서버에 저장되어 승인 요청으로 수량·상품을 바꿀 수 없다.
- 미리보기와 실제 실행 모두 같은 `InventoryService.stockCommand`의 검증·계산을 사용한다. 미리보기는 transaction의 쓰기를 버리는 서버 내부 모드이며 호출자가 임의 Firestore 작업을 지정할 수 없다.
- 승인 transaction에서 OAuth access/family의 생존·scope·취소, canonical 직원 권한, 미리보기 만료, 상품/설정의 Firestore updateTime을 확인한다. 재고 버전뿐 아니라 이름·단위 변경이나 같은 수량의 다른 실사 기록도 이전 미리보기를 무효화한다. 이후 기존 재고·원본 이벤트·감사 이력·영구 request receipt가 함께 저장된다.
- 중복 클릭/동시 승인/응답 유실은 같은 plan의 requestId로 재실행해도 한 번만 적용한다. 이미 처리된 승인은 당시 receipt를 반환하며 현재 수량 조회로 표현하지 않는다. 미리보기 문서는24시간 TTL로 정리하고 기존 영구 receipt에 TTL을 추가하지 않는다.
- 쓰기는 서버에서 자동 재시도하지 않는다. `WRITE_RESULT_UNKNOWN`이면 저장됐을 수 있으므로 같은 미리보기로 결과를 재확인한다. 새 변경을 즉시 만들지 않는다. 만료/충돌은 최신 자료로 새 미리보기가 필요하다. 접근 취소 뒤에는 결과도 공개하지 않는다.

기존 runtime SA/IAM을 확장하지 않는다. SA 이름에는 readonly가 남아 있지만 원래부터 OAuth/PIN 기록을 위해 Firestore datastore.user 권한을 갖고 있었다. 실제 업무 쓰기 제한은 OAuth scope, UI capability, canonical 서비스 역할/transaction 경계가 담당한다. 기존 Callable App Check/Rules를 바꾸거나 Firebase 클라이언트 직접 쓰기를 추가하지 않는다.

## 검증과 운영

`npm run test:mcp:emulator`는 demo Firebase만 사용하여 각 쓰기·미리보기 무변경·충돌·중복·만료·권한/동의 취소·원본 이력·공식 MCP HTTP 계약을 검증한다. `npm run test:mcp:browser`는 사진 회귀와 Chromium/WebKit 승인 UI의 터치 영역·스크립트 주입 방지·명시적 클릭·중복 차단을 검사한다. 별도 실물 모바일 원격 장치는 없어 실제 Android/iOS ChatGPT 앱 검증으로 주장하지 않는다.

운영에서는 인덱스 Query Explain, 기존 자료 읽기, 승인하지 않는 미리보기와 ChatGPT 표시만 확인한다. 검증용 운영 재고 수정은 금지한다. 단위 테스트/에뮬레이터 통과를 모든 기기/호스트/네트워크에서의 완벽성이나 항상 같은 속도로 표현하지 않는다. 사용자 문의 시 개인정보·PIN·token·상품 원문 없이 requestId/도구/오류코드/시간/읽기 수/응답 크기만 사용한다.
