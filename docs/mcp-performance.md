# MCP 업무 조회·사진 UI 성능 — 1.11.0

## 1.11.0 원문 거래처 카드

상세 카드는 같은 structuredContent를 직접 표시하며 업무 API 추가 호출0·외부 네트워크0이다. 비공개 metadata에 같은 주소/연락처를 복제하지 않는다. 표준 MCP App과 ChatGPT toolOutput을 지원하고 취소/오류/미확정 결과에서는 이전 값을 지운다. 호스트 높이·안전 영역·회전에 맞게 자체 스크롤한다. 정적 resources/read와 OAuth 요청은 업무 tools/call 건수와 구분한다. 모델의 텍스트가 업무 원문을 축약할 수 있으므로 원문 카드 표시도 실제 검증 대상으로 삼는다.

## 1.10.0 거래처 상세정보와 선택 항목

`get_customer_details`는 기존 이름 검색과 권한 transaction 상세 읽기를 한 도구로 묶는다. 확인된 ID는 이름 카탈로그를 생략하며 주소/연락처/납품 안내/변경 안내 중 필요한 항목만 반환할 수 있다. 검색 후보와 원본은 별도 시점일 수 있으므로 상세는 항상 현재 원본을 다시 읽는다. 원본이 사라지거나 기본 조건에서 폐업되면 예전 후보로 대신하지 않는다. 공백/구두점 검색이 전체 거래처와 일치하는 문제도 차단했다.

서비스의 ID 상세 읽기는 기존 canonical 권한2문서+거래처1문서이며 OAuth/rate limit/응답 전 재인가 읽기는 별도다. 선택 항목은 응답을 줄일 뿐 기존 상세 문서 읽기를 바꾸지 않는다. 기본 compact는 structuredContent 전체+text 짧은 안내이며 JSON 호환을 유지한다. 출입 비밀번호 기본 제외·요청 항목/미등록 구분·폐업 경고·현재 수정시각 의미와 권한 취소 검증을 함께 적용했다. 새로운 인덱스·DB·인가/개인정보 캐시는 없다.

공식 SDK의 합성490거래처 검사: 검색+상세2회→직접 상세1회, 두 경로의 카탈로그 관측491문서는 같다. 이미 확인한 ID는 카탈로그0/상세 서비스1회다. 동일 ID 전체 응답 JSON8,308B→compact4,456B, 연락처만1,955B다. 합성 긴 납품 안내를 가진 데이터의 전송 바이트이며 운영 응답시간/청구액/토큰 절감률로 해석하지 않는다. `scripts/benchmark-mcp-customers.mjs`를 CI에 추가했다. 실제 측정과 검증 범위는 최신 HANDOFF를 따른다.

## 1.9.0 거래처 이름과 최초 갤러리 연결

`get_delivery_gallery`는 이름(query) 또는 이미 확인한 거래처 ID를 받는다. 이름 검색→기록 조회→첫 썸네일을 한 도구 응답에 포함해 모델의 검색/요약/사진별 호출과 첫 UI 이미지 호출을 줄였다. 표준 image content와 widget metadata를 함께 제공하며 이미지의 두 경로 전송 비용은 유지한다. 전체 검색 완료·처음부터 검색·유일한 후보를 모두 확인한 경우만 자동 선택한다. 등록명에 추가된 업종 접미 표현과 명시적 법인 표기만 제한적으로 처리하고 다른 이름이나 오타를 추정하지 않는다.

검색은 기존 서비스의 bounded scan을 재사용하되 이름·검색 필드·상태·지역7필드만 Firestore projection으로 읽는다. 연락처·출입 비밀번호·주소·사진·일반 업무 메모는 검색 과정에서 다운로드하지 않는다. 문서 읽기 건수를 줄이는 인덱스 검색으로 바꾼 것은 아니며 최대5페이지/5초와 정확한 커서를 보존한다. 별도 DB·복제·인가/재고 캐시·인덱스·운영 backfill은 추가하지 않았다.

공용 UI v9에서 최초 썸네일은 추가 호출 없이 표시한다. 사용자 전환마다 해당 이미지의 기존 권한·삭제·만료 상태를 다시 확인한다. 7일 보관, 직원 필터와 등록시각 의미, 모바일 독립 툴바, 기존 직원 최신 갤러리와 재고 사진/승인 기능은 유지한다. 실제 운영 측정과 검증 한계는 최신 HANDOFF 기록을 따른다.

현재 구현과 안전한 저장은 [재고 업무 가이드](mcp-inventory-write.md), 배포/실제 ChatGPT 측정은 [HANDOFF](HANDOFF.md)의 최신 기록을 따른다.

상품 사진은 [상품 사진 가이드](mcp-inventory-photos.md)를 따른다. `get_inventory_photo(query)` 한 번으로 이름 해석과 최초 썸네일을 반환하며 실사 로그·묶음 조회를 생략한다. 이미 확인한 ID는 검색도 생략한다. 썸네일을 기본으로 사용하고 큰 사진은 클릭할 때만 읽는다. 인증/첨부 상태 캐시와 이미지 재가공은 추가하지 않는다.

## 1.7.0 직접 이력 검색과 응답 예산

- 직원/창고/상품/기간 이력은 원본 events 인덱스를 사용하여 전체 상품 순회를 제거한다. 8개 필터 조합 인덱스를 추가하며 기존 문서 backfill·복제 이력·재고 캐시는 없다.
- 이력 기본 응답은 전후 묶음 배열을 생략한다. 건수 요청의 `includeRecords=false`는 개별 행과 상품명 getAll을 생략하고 직원·창고별 페이지 집계만 반환한다. 이벤트 읽기와 기록자 이름 확인은 유지한다.
- 합성100이력의 같은 직원/창고 비교는 `scripts/benchmark-mcp-records.mjs`로 검증한다. 원본100건/직원1문서/도구1회는 같고 상품명100→0문서다. 실제 응답 바이트와 운영 표본은 최신 인수인계를 따른다. 이 수치를 토큰/청구액/운영 지연 개선율로 일반화하지 않는다.
- 기존 현황의 창고별 실사 상태는 같은 상품 순회에서 계산하여 추가 업무 읽기 없이 반환한다. 현재 stocktake 상태는 버튼 활동 건수와 구분한다.
- 활성 상품 목록에 field mask를 적용해 내부 inspectionByLot(최대200묶음) 전송/파싱을 제외한다. Firestore 문서 읽기 과금은 줄지 않는다. 원래 PWA 목록은 바꾸지 않는다.
- 미리보기/승인은 횟수 감소보다 정확성과 중복 방지가 우선이다. read token은 계속 유효하고 write scope는 별도 동의가 필요하다. 쓰기 실패를 자동 재시도하지 않고 결과 불명이면 같은 plan의 영구 receipt로 확인한다.

아래는 이전 단계의 구현/측정 기록이며 현재 쓰기 지원 여부는 위1.7 가이드가 우선한다.

## 1.6.2 기록자·공통 요청 지연 개선

- 도구 오류는 `isError=true`, `content`의 JSON `{status:"error",error:{code,message,retryable,retryAfterSeconds}}`로 전달하며 UI용 `_meta.error`에도 안전한 상세를 제공한다. 성공 전용 `outputSchema`와 충돌하는 `structuredContent`는 오류에 넣지 않는다. 도구 목록을 먼저 읽은 공식 SDK가 오류를 스키마 오류로 바꾸는 문제를 수정했다. 사진 UI v7은 새 오류와 기존 structured 오류를 모두 해석하며 인증 취소 시 이미지 제거/만료 안내를 유지한다.

- `lastStocktake.actorEmployeeId`는 원본 수량일치 로그, `actorName`은 그 ID로 읽은 **현재 직원 명부의 표시 이름**이다. 당시 이름 스냅샷은 저장되어 있지 않다. `actorNameSource=current_employee_directory`로 출처를 구분하고 이름/직원/기록자 ID가 없으면 `actorName=null`, `actorNameSource=unavailable`을 반환한다. 로그가 없다는 뜻의 `lastStocktake=null`과 다르다. 현재 로그인 사용자나 상품 수정자로 보충하지 않는다. 비활성 직원도 남아 있는 이름은 확인할 수 있다.
- 검색·일괄·상세·부족·알림·현황 예시 모두 같은 응답에 기록자를 포함한다. 반환 제품의 원본 로그를 조회한 뒤 중복 직원 ID를 제거하고 `employees`의 `displayName`만 getAll 한 번으로 읽는다. 100제품을 같은 직원이 확인했다면 명부100회 대신1문서/1RPC이며, 기록자 ID가 없으면 명부 읽기0회다. 원본 이벤트는 기존 제품별 최신1건 쿼리/동시8개를 유지한다. 조회 실패를 이름 없음으로 숨기지 않는다. 문서 ID 일괄 조회이므로 새 인덱스·backfill·업무 쓰기가 없다.
- 기존 운영 표본 1.6.1 검색은 전체1,626ms 중 authorization 누적1,284ms였고 Auth 조회3회였다. 같은 HTTP 요청에서 gateway가 완료한 인증을 첫 도구 실행 전 확인으로 한 번만 사용한다. 정상 도구 호출의 OAuth/Auth 확인은3→2회, 인증 문서 읽기는12→8개(요청 제한/업무 읽기 제외)다. 응답 직전·재시도 전에는 새로 검사하고, 다음 HTTP 요청/다른 전송 방식/추가 도구 호출에는 재사용하지 않는다. 계정·권한·토큰 취소/만료 확인을 위한 TTL 캐시를 두지 않는다. 새 ChatGPT 검색1회/2제품 표본은1,108ms/Auth2회/94문서/3,413B로 기록자까지 원본과 일치했다. 이전 동일 검색 표본1,626ms/Auth3회/97문서/2,996B와 비교하되 응답417B는 기록자·출처 추가로 증가했다. 단일 warm 표본이며 추론·호스트 시간과 총청구액은 포함하지 않는다.
- 카탈로그 부분 문자열·초성 검색의 범위를 임의로 줄이면 누락될 수 있으므로 기존 bounded scan과 부분 결과/커서 계약을 유지한다. 정확성을 희생하는 재고 캐시·인증 캐시와 상시 인스턴스 비용 증가는 적용하지 않았다. 여러 상품 묶음 검색, 요약 응답, compact 형식 및 직원별 직접 사진 쿼리를 우선 사용한다. 사진 원본 전송과 ChatGPT 추론/호스트 지연은 별도이며 모든 질문의 응답시간을 보장하지 않는다.

안전재고가 없으므로 부족 기준은 기본 합계0, 장소 합계에는 샘플도 포함한다. 유통기한 알림은 서울 오늘~`days`일 뒤까지(양끝 포함), 이미 경과한 날짜도 포함한다. 수량이 남은 장소의 **가장 빠른 유통기한**을 사용하므로 장소 전체 수량이 그날 만료되는 것으로 해석하면 안 된다. 날짜 미등록은 임박 판단 대상에서 제외되며 상세 조회에서 확인한다. 납품사진은 기존168시간 보관 범위이며 현재 연결된 상품 대표 사진에는 이 제한을 적용하지 않는다.

## 재고 실사 날짜와 비용 경계 (1.6.1)

`lastStocktakeAt`은 **제품별 ‘수량 일치 확인’ 버튼이 저장한 마지막 `count_match` 이벤트의 `createdAt`**이다. `lastStocktake`에 원본의 이벤트 ID·제품 ID·종류·시각·장소·주기·재고 버전을 함께 제공한다. 다른 장소의 완료 여부와 무관하다. 입출고·수량조정·상품 수정시각이나 장소별 완료 요약으로 버튼 기록을 추정하지 않는다. null은 해당 버튼 이벤트가 없다는 뜻이다. 기록자 ID는 원본 연결용으로 반환하되 일반 답변에는 이름만 표시한다. 메모·묶음 내역은 반환하지 않는다. 기존 `stocktakeByLocation`/현황의 실사 상태는 입출고도 반영하는 PWA 완료 규칙이며 버튼 로그와 구분한다. **1.6.0은 장소별 요약을 사용했지만 사용자 정정에 따라 원본 로그 기준으로 바꿨다.**

기존 `inventoryProducts/{productId}/events`에 `kind=count_match`, `createdAt DESC, __name__ DESC`, limit1 쿼리를 실행한다. 새 COLLECTION 범위 복합 인덱스1개만 추가하고 기존11개를 보존했다. 운영 Query Explain도 해당 인덱스를 사용한다. 제품별 이력 전체나 검색에 탈락한 상품의 로그는 읽지 않는다. 반환된 상품별 쿼리1회가 추가되며 최대8개 동시 읽기로 제한한다. 현황은 중복 제거한 예시 제품(최대30개)만 조회하고 exampleLimit0이면 로그 조회0이다. 빈 쿼리도 Firestore 최소 읽기 비용이 있으며 계측 snapshot0과 비용0을 혼동하지 않는다. 새로운 요약 문서나 캐시/쓰기·backfill 없이 기존 버튼 로그를 직접 읽기 위한 비용이다. 쿼리 실패는 도구 오류로 반환하고 ‘기록 없음’으로 바꾸지 않는다.

수량과 버튼 로그는 별도 읽기이며 동일 시점 transaction을 보장하지 않는다. 수량 자체의 일괄 transaction과 조회 전후 권한 검증은 유지한다. `updatedAt`은 상품 정보/수량/확인 등 문서 수정 시각이므로 정확한 수량 변경일이나 실사일로 대신 쓰지 않는다. 버튼과 기존 실사 업무 규칙은 변경하지 않았다.

여러 이름을 각각 검색하면 같은 카탈로그를 반복 읽는다. `queries`는 최대10개 검색어를 함께 평가하고 겹치는 상품을 한 번만 반환한다. `matches`는 이번 응답에 포함된 상품 ID만 연결한다. 부분 검색의 빈 matches는 상품 없음이 아니며 같은 전체 검색어와 커서로 계속한다. 단일 `query`는 계속 지원한다. 검색 결과에 현재 수량/시각이 있으므로 단순 질문에는 추가 상세 조회를 하지 않는다.

MCP 검색·알림·현황은 `status=active` 조건을 Firestore에 전달해 비활성 상품 읽기를 피한다. 운영 Query Explain에서 기존 `(status ASC, __name__ ASC)` 인덱스를 사용함을 확인했으며 추가 인덱스나 PWA 목록 계약 변경은 없다. 활성 상품 내 이름 검색은 여전히 순차 검색이다. `get_inventory_product(includeLots:false)`는 기존 인가된 상품 transaction만 실행하며 `lots:null/lotsIncluded:false`로 생략을 표시한다. 기본 true와 기존 상세 조회는 유지한다.

`get_inventory_overview`의 집계는 상품 요약과 실사 설정1문서를 사용하고, 예시 제품에만 최신 버튼 로그를 더한다. 묶음·전체 이력·사진은 읽지 않는다. 최대500활성 상품/5페이지/페이지 경계5초로 제한한다. `countScope=returned_scan_segment`와 page/cursor를 확인하고 후속 구간은 이전 집계에 더한다. 소수 예시(기본5/최대10)는 ID 순서이며 전체나 심각도 순위가 아니다. 예시가 잘렸는지는 `examplesTruncated`를 확인한다. 서로 다른 단위의 총수량을 만들지 않는다. 큰 목록 대신 요약해 전송량과 모델 입력을 줄이지만 상품 스캔 자체를 없애지는 않는다. 실사 상태별 품목 수는 PWA 완료 판정이며 버튼을 누른 제품 수로 해석하지 않는다.

재고 도구 기본 응답은 `structuredContent`에 전체 결과를 한 번만 담고 text에는 짧은 요약을 넣는다. text 전용 클라이언트는 `responseFormat:json`을 사용한다. 권한·재고 캐시, 새로운 DB/계정/쓰기 경로는 없고 매 요청 기존 인증을 유지한다. HTTP 전송량 감소를 토큰 수나 청구액 감소율과 동일시하지 않는다.

Functions build 후 `node scripts/benchmark-mcp-inventory.mjs`로 공식 MCP SDK를 사용한 합성490상품 검사를 실행한다. Firebase/네트워크/실사용 자료를 사용하지 않으며 CI에도 같은 읽기·응답 예산 검사를 추가했다.

## 조회 범위와 정확성

- 공용 `CustomerService.search`, `InventoryService.search/lowStock/alerts`에서 기존 페이지·검색 규칙을 재사용한다. 새 DB·검색 서버·파생 문서·운영 데이터 migration은 없다. PWA Callable의 입력/출력 계약은 유지한다.
- 서버가 최대5페이지를 읽는다. 거래처는 페이지당250개, 상품은100개이며 lookahead 문서가 별도로 읽힐 수 있다. 기본 반환50개, 최대100개다. 5초 검색 예산은 페이지 경계에서 검사하고, 전체 도구 처리는20초로 제한한다.
- `page.returnedCount`는 이번 응답의 건수다. `complete=false`/`hasMore=true`이면 빈 결과여도 다음 커서로 계속 조회해야 한다. `startedFromBeginning=false`인 마지막 응답은 앞선 응답과 합쳐야 전체다. `stoppedBecause`는 완료/결과 한도/페이지 예산/시간 예산을 구분한다.
- 한 페이지 중간에서 결과 한도에 도달하면 마지막으로 확인한 항목 뒤에서 재개한다. 삭제로 비어 있는 페이지도 원본 커서로 전진한다. 같은 조건으로 계속 조회해야 하며 검색어·필터가 바뀌면 커서를 초기화한다.
- 여러 페이지는 동일 시점 스냅샷이 아니다. 조회 도중 변경된 수량은 최종 상세 또는 일괄 조회로 확인한다. 상품 일괄 조회는20개 이내를 같은 transaction에서 읽고 삭제/없는 ID를 `missingProductIds`로 구분한다.
- 거래처 납품 요약의 `ambiguous`는 후보 선택이 필요하고, `incomplete_search`는 전체 검색 전이므로 자동 선택하지 않는다. 이름만으로 아직 확인하지 않은 거래처를 추측하지 않는다.
- 응답 스키마를13개 도구 모두에 등록하고 실제 반환값도 검증한다. `retrievedAt`, `timezone`, 단위, 조회 조건과 완료 여부를 유지한다. 민감한 고객 필드를 projection 밖으로 노출하지 않는다.

이 변경은 모델과 서버 사이의 반복 호출을 줄인다. 거래처/상품의 원본 이름 검색은 여전히 순차 스캔이므로 데이터 증가에 비례해 읽기가 늘어난다. 큰 카탈로그를 위한 인덱스·별칭 도입은 사용량 계측 후 기존 서비스/데이터 설계에서 별도로 진행한다.

## 직원별 직접 검색

이전에는 직원별 마지막 사진을 찾기 위해 거래처 검색과 거래처별 목록 호출이 필요했다. 1.4.0은 직원 디렉터리 접두어 인덱스(최대21개) → `createdByEmployeeId`/`createdAt` 복합 인덱스 → 대상 거래처 단건 조회로 처리한다. 직원만 지정하면 거래처 수에 비례한 전체 순회가 없다. `search_delivery_records`의 여러 거래처 이름은 중복을 제거한 최대100개 ID를 한 transaction의 getAll로 읽는다. 거래처 **이름 조건** 해석은 기존 검색을 그대로 재사용하므로 그 단계의 카탈로그 스캔은 남는다.

새 인덱스4개는 active + (조건 없음 / 직원 / 거래처 / 직원과 거래처) + 등록 시각 DESC + 문서 ID DESC를 지원한다. 서버가 createdAt 범위를 최근168시간·서울 날짜·현재 시각으로 제한하고 만료를 다시 확인한다. 조건별 인덱스 READY뿐 아니라 운영 Query Explain 계획을 확인한다. Explain의 index/doc scan 및 executionDuration은 Firestore 쿼리만의 값이며 전체 MCP handler와 구분한다.

최신 직원 갤러리는 **한 tools/call 응답에 첫 썸네일 포함**이다. OAuth·initialize·UI resources/read는 별도 프로토콜 요청이며 업무 조회 호출 수에 포함하지 않는다. 최초 UI 표시 후 다른 사진/확대/페이지는 기존 인증 도구를 호출한다. 일반 `get_delivery_gallery`의 메타데이터 + 현재 썸네일 지연 로딩 동작은 그대로다. 브라우저 검사는 직원 조건이 다른 최초 이미지나 다음 페이지를 거부하고, 올바른 최초 썸네일에서는 추가 호출0을 확인한다.

직원 후보가 둘 이상이거나 검색이 미완료이면 갤러리를 자동 표시하지 않는다. 삭제/만료 행으로 예산을 소진한 경우도 빈 확정 결과로 응답하지 않는다. 정확성 검사는 서울 자정 경계·동시각 ID 정렬·페이지 커서·다른 직원/거래처·삭제·expired active·7일 초과·미래 등록을 포함한다. `registeredAt`과 `deliveryCompletedAt:null`을 명시하며 실제 납품완료 시각을 추정하지 않는다.

## 사진 갤러리의 전송량·상태 경계

1.3.0은 기본50장(최대100장)의 메타데이터만 첫 갤러리 결과에 담고, UI가 현재 사진의 썸네일만 요청한다. 큰 사진은 클릭한 경우에만 내려받는다. 이동 요청은 동시에 하나만 처리하며 빠른 연속 선택은 마지막 선택으로 합친다. 배율 변경은 로컬 계산으로 처리하므로 네트워크 요청이 없다. 사용자가 더 보기를 선택하면 동일 필터의 다음 커서를 같은 UI에 이어 붙인다. 부분 페이지·빈 페이지를 전체 결과로 오인하지 않는다.

등록 시각/기록자는 기존 사진의 동일 권한 검사 결과를 재사용한다. 업체명은 `CustomerService.read(customerId, actor, true)`로 현재 이름을 조회한다. 이 추가 transaction은 권한2문서+거래처1문서의 관측 읽기를 더한다. 폐업 업체도 명시적 옵션일 때만 읽으며 기존 기본 동작은 그대로다. 일반 거래처 갤러리는 직원 이름을 추가 조회하지 않는다. 이미지 복제와 새 업무 데이터는 없다. 갤러리는 업체 조회와 기존 사진 목록 조회를 병렬로 실행한 뒤 외곽 권한을 재검사한다.

UI 메모리에 현재 썸네일/큰 사진만 보관하며 다음 사진을 미리 내려받거나 브라우저 저장소에 저장하지 않는다. 닫기·선택 변경 뒤 늦은 응답을 버리고 호스트가 반복 전달한 UI 호출 결과가 갤러리를 단일 사진으로 바꾸지 않게 처리한다. 기존 응답28MiB·도구20초·권한/보관기간 검사 한도를 유지한다.

1.5.0의 모바일 뷰어는 전체화면 중 hidden 카드의 높이를 호스트에 다시 보내던 동작을 제거했다. 툴바와 사진의 크기 계산을 분리하고 host context/VisualViewport/회전 시 로컬 배치만 갱신한다. 배율·팬·핀치·화면 크기 변경은 추가 도구 호출을 만들지 않는다. 다음 사진/evidence 조회는 기존 OAuth·권한·168시간 보관 검사 경로를 그대로 사용한다. 썸네일과 큰 사진의 전송량, 도구12개와 DB 인덱스는 변경하지 않았다.

## 오류와 권한

- `isError=true`일 때 `_meta.error`와 text content JSON에 고정 오류 코드·안내·`retryable`·`retryAfterSeconds`를 제공한다. 인증 만료, 권한 거부, 자료 없음, 입력 오류, 자료 상태 오류, 호출 제한, 일시 장애, 시간 초과를 구분한다. 원본 SDK 오류·경로·입력 내용은 응답/로그에 넣지 않는다.
- 일시적인 읽기 실패(unavailable/aborted)만250ms 뒤 최대1회 재시도한다. 재시도 전에도 권한을 다시 확인하며 전체20초 제한을 연장하지 않는다. PIN 제출·토큰 교환·refresh를 자동 재시도하지 않는다.
- 시간 초과는 늦게 끝난 결과를 반환하지 않고 다음 관측 대상 I/O를 차단한다. 이미 진행 중인 SDK I/O 자체가 즉시 취소된다는 보장은 없다.

## 성능 관측

Cloud Logging에 `jsonPayload.event="mcp_request"`, `version="1.6.1"`의 구조화 로그를 남긴다. 도구명·고정 오류 코드·시간·건수·크기만 포함하며 PIN, 토큰, 직원/거래처/상품 ID, 이름, 검색어, 사진, 원본 오류를 기록하지 않는다. 임의 request ID를 로그 키로 수용하지 않고 서버가 UUID를 발급한다.

| 항목 | 의미 |
|---|---|
| `durationMs` | 서버 handler 시간. ChatGPT 추론·인터넷 왕복·플랫폼 시작 시간은 제외 |
| `coldStart` | 이 함수 인스턴스에서 관측한 첫 HTTP 요청 표시. 별도 콜드 스타트 전체 시간은 아님 |
| `stageMs` | authorization/query/rateLimit 및 Firestore/Storage/Firebase Auth의 누적 호출 시간. 병렬/중첩되므로 서로 더해 전체 시간으로 사용하지 않음 |
| `documentReads` | 계측한 요청에서 반환된 문서 snapshot 수(없는 문서 조회 포함). 청구량/인덱스 읽기/SDK 내부 재시도 전체를 나타내지 않음 |
| `documentWriteAttempts` | OAuth/호출 제한 메타데이터 쓰기 시도. transaction 재시도로 늘어날 수 있음 |
| `storageBytes`, `responseBytes` | 읽은 이미지 크기, HTTP 응답 크기 |
| `outcome`, `retries`, `complete` | 성공/도구 오류/프로토콜 거부/취소, 재시도 횟수, 조회 완료 여부 |

`readMetricsScope=mcp_reads`인 MCP 경로를 분석한다. 로그인 등 다른 경로의 읽기 계측은 partial이다. 지표 실패가 업무 응답을 막지 않으며 동시 요청의 관측 상태는 분리한다.

인증된 운영 환경에서 집계 예:

```sh
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="employeemcp" AND jsonPayload.event="mcp_request" AND jsonPayload.version="1.6.1"' --project=onnuriway --freshness=1d --limit=1000 --format=json > mcp-metrics.json
node scripts/report-mcp-metrics.mjs mcp-metrics.json
```

집계 스크립트는 버전/도구별 성공·실패·재시도·부분 결과, warm 성공 요청의 p50/p95와 평균 관측 읽기/응답 크기/단계 시간을 출력한다. 작은 표본의 p95를 서비스 성능 보장으로 해석하지 않는다. 사용자 체감 시간은 실제 ChatGPT에서 별도 확인한다.
