# Phase 47 — 재고 현장 사용성 리뉴얼

## 범위와 데이터 안전성

2026-09-13 요청의 14개 항목을 대상으로 기존 밝고 은은한 급식길 디자인을 유지했다. 학교·영업·거래처의 화면 구성은 바꾸지 않으며, 사진 원본 읽기 보완만 거래처와 공유한다. 운영 품목·수량·사진을 검증용으로 변경하지 않는다.

- 홈: 큰 소개 제목, 계산기, 수동 새로고침, 미확인 버튼/선택 필터, 마지막 갱신 안내 제거.
- 구역: 전체 / 냉장 / 냉동1 / 냉동2 / 샘플. 전체는 제품당 한 카드이며 수량을 합산한다. 각 구역 수량은 실제 저장 경계로 유지한다.
- 실사: KST 지정 실사일에만 진행률과 미완료 강조. 여러 구역에 있는 품목은 대상 구역 모두 확인해야 전체 완료이며, 후속 재고 변동이 있으면 다시 미완료다.
- 검색과 임박 토글을 같은 높이에 배치. 기본 임박 기준 D-100일은 유지하며 품절·날짜 미등록은 임박으로 분류하지 않는다. 기한이 지난 재고는 포함한다.
- 목록: 사진·이름·구역·제조사·기준 단위·유통기한 날짜·현재 수량. 임박 상품만 D 배지, 박스 환산 제거. 카드 radius 7px, 간격 5px, 기본 터치 타깃 44px 이상.
- 새 품목: 오른쪽 하단 반투명 고정 액션. 마지막 카드와 더 보기 버튼이 가려지지 않게 하단 스크롤 공간을 확보한다.
- 등록/입출고/조정/실사: 기준 단위 하나로 수량 입력. 신규 제품의 내부 unitsPerBox는 1, 기존 제품 값과 수량·이력은 변환하지 않는다.
- 상세: 출고·입고·조정·수량 확인을 고정 액션으로 구분하고, 정보 수정·이력·관리 작업을 펼쳐서 제공. 보관 장소 이동/계산기 진입과 미사용 계산기 코드는 제거한다.
- 비활성화/삭제는 기존 관리자 권한과 화면의 안전조건 유지. 비활성화는 수량 0, 삭제는 수량과 이력이 없는 제품만 가능하다. 이력이 있는 품목은 삭제 대신 비활성화한다. 최종 교차 검토에서 화면에만 있던 이력품 삭제 제한을 서버에도 추가했다. 기존에 확정된 삭제 receipt의 재시도는 호환 유지한다. 기존 입출고 이력을 지우거나 직원 권한을 확장하지 않는다.

## 사진 원본 읽기

실패 문구는 업로드/압축 이전의 원본 바이트 읽기 단계에서 발생한다. 확인한 코드 취약 경로를 다음처럼 보완했다.

1. `arrayBuffer` 실패뿐 아니라 불완전한 바이트 결과도 FileReader로 재시도한다.
2. 각 읽기를 시간 제한과 취소로 보호하고, 완료되지 않은 읽기로 폼이 계속 잠기지 않게 한다.
3. 원본을 메모리 파일로 복사하기 전까지 native file input을 초기화하거나 비활성화하지 않는다.
4. 동기 중복 선택/화면 종료/늦게 도착한 결과를 차단하고 기존 미리보기 URL을 정리한다.
5. 실패 때 ‘파일에서 선택’ 대체 경로를 제공하며 확장자 대신 실제 파일 내용을 검증한다.

Galaxy S20+의 앨범 content URI 자체는 데스크톱에서 재현하지 못했다. Google Keep 경유 첨부 JPEG 2,215,707B는 실제 Chrome에서 두 picker 모두 1920×2560 WebP(약 1.10MB)로 준비됐다. 이 성공을 휴대폰 원본 80% 실패의 원인이 완전히 확정·해결되었다는 근거로 사용하지 않는다.

[W3C File API](https://www.w3.org/TR/FileAPI/#dfn-error-names)는 파일의 읽기 접근/상태 오류를 별도로 정의한다. 원본 읽기 문제를 HEIC 또는 특정 휴대폰의 문제로 단정하지 않았다.

## 저장 지연과 재시도 정확성

- 인증의 동일 문서 중복 읽기를 `getAll`로 통합: 일반 직원 3→2문서, 관리자 6→2문서. 사전·트랜잭션 내부·사후의 모든 권한 검증 시점, Google 관리자 승인 조건, 세션/권한 버전 비교는 유지한다.
- 실사에서 독립적인 상품·설정·재고 읽기를 병렬화한다.
- 입출고/실사/유통기한 수정의 opt-in `includeDetail`은 동일 트랜잭션에서 확정된 active lots까지 반환한다. 정상 응답 뒤 상세 재조회 API 1회를 생략한다.
- receipt 재시도에는 상세 스냅샷을 재사용하지 않는다. 최신 상세 조회에 성공한 뒤에만 부모 목록을 갱신하며, 늦은 조회가 새 저장 결과를 덮지 못하게 한다.
- 등록/정보 수정/상태/삭제의 `refreshOnReplay`는 재시도에만 최신 상품 문서를 읽는다. 정상 저장에 추가 요청/읽기를 붙이지 않고, 원본 receipt/입고/감사 이력은 재작성하지 않는다.
- 앱으로 돌아올 때 60초 이상 지난 목록은 1회 갱신한다. 전체 목록 주기 폴링, 오프라인 자동 제출, 인증 영구 캐시, 유료 상시 인스턴스를 추가하지 않는다.

[Firebase 공식 성능 가이드](https://firebase.google.com/docs/functions/tips)를 참고했다. 운영 환경에서 특정 초만큼 빨라졌다고 주장하지 않는다. 확실한 개선 근거는 중복 읽기와 API 왕복 제거이며, 최초 함수 기동/통신 속도/사진 전송 시간은 남는다.

## 검증 기록

사용자 흐름: 직원 PIN → 재고 모드 → 사진 포함 최초 등록 → 입고 → 실사 → 출고/조정 → 확정 결과 표시. 별도로 여러 구역 합산, 지정 실사일, 읽기 전용 직원, 관리자 전용 작업 거부, 세션 철회, 오프라인 입력 보존, 1,000개 목록을 검증한다.

- 사진 단위 52개, 기존/신규 브라우저 회귀 26개 통과. 실제 JPEG decode, 부분 읽기, 타임아웃, 파일 형식 거부, 대체 선택 복구 포함.
- 상세 저장 경합 9개와 기존 상세 8개 회귀 통과.
- UI 밀도는 [W3C 터치 타깃 지침](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)을 참고하고, 시각적인 패딩 축소와 실제 터치 영역 축소를 구분했다.
- 삭제 서버 가드 포함 최종 전체 단위 1,260개 통과(125개 파일). 별도 통합 환경이 필요한 11개는 일반 실행에서 제외했다.
- 정적 production 빌드에서 실제 Auth/Functions/Firestore/Storage 에뮬레이터 E2E 6/6 통과. 사진 등록·교체·삭제, 입고→실사→출고→조정, 권한 회수, 오프라인 초안, 여러 구역 합산, 1,000개 목록을 포함한다.
- 같은 격리 환경에서 실제 Firestore 트랜잭션 통합 8/8 통과. 원자 저장·동시 재시도·롤백·확정 상세 반환·재시도의 최신 상품 반환을 확인했다.
- 360/768/1280px에서 검색/스위치 높이 48px, 가로 넘침/상호 겹침 없음, FAB 고정 및 마지막 카드/더 보기 접근을 확인했다. 수량 저장 확정 후 추가 상세 조회는 0회였다.
- 최종 ESLint·TypeScript·diff 검사·운영 빌드·성능·PWA·Hosting 정적 게이트 통과.

## 번들 예산

미사용 제목·박스 계산·계산기 UI/CSS를 제거했다. 재고 CSS 4KiB와 JS 24KiB, 초기·학교·영업 CSS/JS 기존 한도를 유지한다. 공유 사진 읽기 복구 코드로 거래처 지연 로딩 JS가 35,876B gzip으로 증가해 거래처 JS 한도만 34.5→35.5KiB(1KiB)로 제한적으로 조정했다. 새 패키지는 추가하지 않았다.

최종 측정: 최초 JS 140,742B gzip, 재고 JS 19,698B(이전 20,492B), 재고 CSS 3,996B(이전 4,084B). 정적 파일 97개, PWA precache 68개.

## 배포 순서

새 선택 입력값은 구 서버의 strict 스키마가 거절하므로 **재고 Functions 먼저, Hosting 다음** 순서로 배포한다. Firebase `onnuriway` Standard/Seoul의 기존 데이터베이스와 도메인을 유지한다. 보안 규칙·인덱스·유료 최소 인스턴스는 변경하지 않는다.
