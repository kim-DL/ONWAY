# Phase 49 — 개인 실사 모드와 유통기한별 확인

## 결정과 화면

사용자의 버튼 스케치 중 2안을 적용한다. 자주 쓰는 재고 작업을 첫 줄에 유지하고, 파괴적인 작업을 실수로 누르지 않도록 별도 더보기 대화상자로 옮긴다.

- 고정 하단 1행: 출고 / 입고 / 조정 / 정보 수정.
- 고정 하단 2행: 수량 일치 확인 / 더보기.
- 더보기: 입출고·실사 이력, 비활성화 또는 재활성화, 삭제. 기존 직원 권한과 상태 변경 확인·감사 이력을 유지한다.
- 검색창 아래 ‘비활성 품목 보기’ 옆에 재고조사 모드 토글을 둔다. 직원별 화면 설정이며 공유 운영 설정을 변경하지 않는다. 같은 직원·인증 세션·한국 날짜에만 복원하고 새 날짜나 직원 변경 시 OFF로 시작한다.
- 토글은 기존 재고 쓰기 권한이 있는 모든 직원에게 제공한다. 읽기 전용 계정의 재고 변경 제한을 풀지 않는다.
- 이번 실사 대상이 없는 경우 0/0 진행 카드를 숨긴다. 브라우저 저장소를 사용할 수 없는 환경에서도 같은 화면·직원·날짜의 ON/OFF는 재조회 때문에 꺼지지 않는다.
- 토글 움직임, 체크 표시, ON/OFF 텍스트를 함께 제공한다. 색상만으로 상태를 전달하지 않는다. [WAI-ARIA Switch 지침](https://www.w3.org/WAI/ARIA/apg/patterns/switch/)에 맞춰 고정된 접근성 이름과 네이티브 체크박스의 키보드 조작을 유지한다. 동작 감소와 고대비 설정도 대응한다.
- 목록에 서로 다른 유통기한이 2개 이상인 경우에만 ‘유통기한별 수량 n’을 표시한다. 같은 날짜가 다른 장소에 나뉜 것은 전체 보기에서 중복 날짜로 세지 않는다.
- 입출고·조정의 메모/필수 사유 입력과 긴 정수 안내를 제거하고 입력란에 짧은 예시를 넣는다. 정수·최댓값 검증 자체는 유지한다.
- 날짜별 정보 수정은 날짜 입력/미확인을 먼저 선택하고 날짜를 입력한다. 해당 없음은 새 선택지에서 제거하되, 과거에 저장된 해당 없음 재고를 임의로 변환하지 않는다. 변경하지 않은 저장은 비활성화한다. 날짜 변경을 저장하지 않은 상태에서 수량 작업을 시작하지 않도록 막는다.
- 제품 촬영 전용 입력, 기존 사진 확대, D-100 기준, 테마, 고정 버튼과 모바일 뒤로가기 흐름을 유지한다.

## 실사 판정

사용자가 확인한 기준: 개인별 ON/OFF, 조작한 유통기한만 확인한다.

1. 지정 실사일의 입고·출고·조정은 해당 날짜별 재고만 확인한다. 지정일이 아닌 날은 개인 모드 ON일 때만 명시적으로 확인한다.
2. 수량 일치 확인 버튼은 개인 모드 ON에서만 활성화된다. 날짜별 수량은 읽기 전용이며, 수량을 변경하려면 별도 조정을 사용한다.
3. 한 유통기한은 취소/일치 확인, 여러 유통기한은 날짜별 현재 수량 목록과 취소/수량 일치·실사 완료로 재확인한다. 장부/실측/차이 입력은 없다.
4. 확인창을 열어둔 동안 동료가 수량을 바꾸면 오래된 확인은 거절한다. 서버가 수량·전체 대상·재고 revision·실사 주기를 다시 확인한다.
5. 품목 전체 확인은 실제 대상 유통기한과 보관 장소가 모두 확인되어야 한다. 하나를 조작했다고 나머지를 자동 완료하지 않는다. 이후 일반 재고 변동은 영향을 받은 확인만 무효화한다.
6. 지정 실사일 이후 신규 등록된 품목은 다음 주기가 되기 전까지 미확인으로 표시하지 않는다. 한국 시간 기준의 등록일 경계를 적용한다. 실제로 확인한 완료 표시는 유지한다.
7. 실사 요일 변경으로 주기가 연장되었을 때에도 단순 요일 일치가 아니라 확정된 주기 시작일을 기준으로 자동 확인한다.

## 저장 구조와 호환성

- 기존 트랜잭션에서 읽은 재고로 날짜별 그룹 요약을 계산한다. 목록 카드마다 별도 조회를 추가하지 않는다.
- 공개 `lotSummary`는 `includeSummary: true`를 요청한 새 클라이언트에만 반환한다. 구버전의 엄격한 응답 검증과 재시도 영수증을 유지한다.
- 내부 `inspectionByLot`는 API에 노출하지 않는다. 보유 중인 lot 수 범위로 제한하고 소진된 항목을 정리한다.
- 수량 일치 확인은 `matchOnly: true`를 사용한다. 서버에서 수량 변경을 거절하며 사용자·시각·변경 전후의 불변 이력은 남긴다.
- 조정 사유를 없애도 재고 이벤트/감사 데이터와 권한·App Check·충돌 방지·중복 저장 방지는 유지한다.
- 기존 목록용 요약은 별도 명시적 운영 도구로 보강한다. 실제 수량·revision·수정시각·실사 완료·사진·이력을 변경하지 않고 `lotSummary`만 트랜잭션으로 추가한다.

## 운영 반영

구서버가 새 필드를 거절하지 않도록 전체 재고 callable에 호환 단계를 먼저 적용한 다음 최종 서버, 기존 품목 요약 보강, Hosting 순서로 진행한다. Firebase `onnuriway` / `(default)` / Standard / Seoul을 유지하고 규칙·인덱스·예약 함수·다른 모드는 변경하지 않는다.

- 호환 단계 13개 callable 배포 성공과 전부 ACTIVE를 확인했다. 새 필드를 생성하지 않되 이미 있는 새 필드는 보존하는 격리 패키지를 사용했다. 재고 writer의 60초 timeout 이상을 지난 후 최종 서버 배포를 시작했다.
- 배포 패키지: `.cache/deploy/inventory-compat-phase49-20260913-0910`. 신규 DB 필드가 생긴 이후 서버 롤백이 필요하면 이 호환 패키지를 사용한다. Phase 48의 엄격한 구 파서로 되돌리거나 새 필드를 삭제해서 롤백하지 않는다.
- 운영 보강 도구는 기존 Firebase CLI 로그인만 명시적으로 사용한다. 머신의 다른 프로젝트용 ADC는 사용하지 않는다. 첫 dry-run에서 도구의 auth v9/v10 헤더 형식 불일치를 발견했고, Firestore transport가 내보내는 일치하는 auth 버전으로 수정했다. 실패한 두 dry-run은 조회 단계에서 종료되어 DB 쓰기가 없었다. 헤더 형식과 ADC 우회 회귀 테스트를 추가했다.
- 수정 후 dry-run에서 기존 품목 2개의 문서/lot ID 및 수량 합계 일관성을 확인했다. 이 단계에서는 데이터를 변경하지 않았다.
- 최종 재고 서버 13개 배포 성공 및 모두 ACTIVE를 확인한 뒤 기존 품목 2개에 `lotSummary`만 추가했다. 적용 전후 stockRevision 7/5는 유지됐다. 다시 dry-run해 두 품목 모두 already-summarized, 추가 보강 대상 없음을 확인했다.
- 운영 Hosting에 1차 반영 후 이전 설치 클라이언트의 상세 조회와 새 버전 업데이트, 기존 관리자 로그인 유지 및 재고 조회를 확인했다. 360px에서 날짜별 9봉/30봉·합계 39봉, 배지 2, OFF의 확인 버튼 비활성, ON의 읽기 전용 확인창을 확인했다. 확인창의 input/textarea/select는 0개였다.
- 운영의 더보기/이력·날짜 수정 상태 2개·선택 날짜의 수량 조정 9봉·기존 사진 확대/Back을 점검했다. 저장/실사 완료/상태 변경/사진 업로드는 실행하지 않았고, 목록 복귀 및 개인 토글 OFF를 복원했다. 브라우저 경고/오류 로그는 없었다.

## 성능

미사용·중복 CSS를 먼저 정리한 후 재고 전용 스타일만 28,656B raw / 6,480B gzip으로 측정했다. 개인 토글, 더보기, 읽기 전용 날짜별 확인 및 두 상태 날짜 선택 UI에 한정해 CSS 예산을 28.5KiB / 6.5KiB로 조정했다. 재고 JS 24,122B gzip은 기존 24KiB 예산 안에 있다. 사진 확대 추가 JS는 2,231B, 공유 사진 CSS는 기존 6,711B raw / 1,928B gzip 그대로다.

초기 JS 140,764B gzip, 거래처 JS 35,876B gzip. 초기·학교·영업·거래처·관리자 예산과 지연 로딩 격리 검사는 유지했다. 신규 패키지는 추가하지 않았다. 최종 성능·PWA·Hosting 게이트 통과, 정적 파일 98개 / precache 69개.
