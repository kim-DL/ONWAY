# 사진 등록 집계·경로 저장 확인

## 구현 계획

목표는 명세서/손글씨 사진을 오늘 납품처에 병합할 때 사진별로 `새로 추가 N곳 · 이미 등록 M곳`을 정확하게 보여주고, 경로 추천은 사용자가 `순서 저장`을 눌렀을 때만 저장하는 것이다. 기존 순서·사진·줄임말·권한·request ID·서버 응답 확인 계약을 유지한다. 운영 시험 등록은 하지 않는다.

- 집계의 기준은 **사진을 병합하는 트랜잭션 직전의 해당 직원·해당 날짜의 기존 병합 정책**이다. 오늘 문서가 있으면 저장된 오늘 목록(override가 아니면 내 납품처), 오늘 문서가 없으면 빈 목록을 기준으로 하고, 기존 보존 대상 사진의 거래처를 더한다. 오늘 문서가 없을 때 내 납품처만으로는 기등록으로 세지 않는다. 내 납품처에만 있고 저장된 오늘 목록에 없는 거래처도 오늘 새로 추가로 센다. 기존 병합 정책 자체는 변경하지 않는다.
- 상호 표기/사진 장수/행 개수가 아닌 연결된 거래처 ID를 중복 제거한다. 한 사진의 새로 추가와 이미 등록 집합은 겹치지 않는다. 오늘 목록의 기존 순서는 보존하고 신규만 뒤에 추가한다.
- 자동 연결과 여러 번 나눠 하는 수동 확인의 집계를 사진 단위로 누적한다. 먼저 새로 추가된 ID가 이후 행에서 다시 확인되어도 새로 추가 한 곳으로 유지한다. 별도 사진에서 같은 ID를 다시 연결하면 그 사진에서는 이미 등록 한 곳이다. 같은 요청 재시도는 저장된 결과와 집계를 그대로 반환한다.
- `PhotoBatchResult`는 strict 스키마를 쓰는 구버전 앱과 공존한다. 공개 필드를 추가하지 않고 기존 `message`에 집계 문구를 담는다. 화면은 기존 결과 안내 위치를 재사용하고, 상단/하단 전체 연결 수는 `연결`로 표현한다. 집계가 있는 결과는 연결이 완료된 ID만 포함하며 아직 확인할 행은 별도 확인 수를 유지한다.
- 최초/추가 병합 시 분류한 ID 집합은 기존 scan requestLock의 **result 밖** 내부 `registration`에 저장한다. 추가 병합 전까지 저장된 행의 모든 ID를 내부 집계가 설명하는지 확인한다. 과거 scan에 내부 집계가 없거나 일부가 누락되면 과거 추가/기존 여부를 추측하지 않고 해당 사진의 정확 집계 표시를 생략한다. 과거 저장 행이 전혀 없으면 이후 확인부터 정확 집계가 가능하다. 공개 result와 이전 요청 receipt는 변경하지 않는다.
- `addCustomers`의 private 반환만 `{lists, registration}`으로 바꾸고 기존 명세서 API 두 곳은 `lists`만 사용한다. 추가/집계·scan 결과·줄임말·감사 기록은 같은 기존 트랜잭션 안에서 완료된다. 실패/100곳 초과/권한 변경은 전체 롤백한다.
- 경로 미리보기는 저장하지 않는다. 저장 응답이 유실되면 같은 추천 ID와 request ID로 재확인하고, 바뀐 목록/만료 추천은 기존 서버 검증을 유지한다. 닫기는 미저장이다.
- 카카오 주소 검색과 길안내는 표시된 등록 주소를 기준으로 확인한다. 도로명/지번/층수 포함 주소 검색, 후보 선택 후 주소·좌표·지도 갱신, 길안내 좌표 URL 순서와 실패 처리, 운영 두 도메인 호환을 점검한다. 실제 휴대폰 내비게이션 실행·실주행 증거와 데스크톱 확인은 구분한다.
