## 거래처 등록 주소 검색

운영 `https://onnuriway.com`의 새 거래처 등록 화면에서 검색·결과 선택을 확인했다. 거래처 저장은 누르지 않았고 점검용 탭만 닫았다.

주소 검색은 `CustomerEditor.findLocations → customerRepository.searchLocations → searchCustomerLocations` Callable을 사용한다. 서버는 카카오 주소 검색과 장소 검색 결과를 함께 제공하고, 요청 권한을 결과 반환 전에도 다시 확인한다. 선택한 주소·좌표를 draft에 반영한 뒤 역지오코딩은 구·동 보완에만 사용해 도로명을 덮어쓰지 않는다. 이번 확인 범위에서 기능 결함이 없어 주소 검색 코드는 수정하지 않았다. 모든 주소나 실물 휴대폰에서의 정상 동작을 보증한 시험은 아니다.

## 추천 순서 확인 후 저장

기존에는 추천 응답을 받은 즉시 `applyDeliveryRoute`를 호출했다. 이제 결과만 표시하고 `저장할까요?`와 `순서 저장`을 보여준다. 사용자가 이 버튼을 누른 뒤에만 기존 저장 Callable을 실행한다. `창 닫기` 또는 닫기 버튼으로 나가면 미확인 추천 순서는 저장하지 않는다. 명세서·손글씨의 정확한 상호 자동 등록은 기존대로 유지했다.

저장 완료는 서버 응답 후 표시한다. 응답 유실·실패 때는 `저장 다시 확인`으로 같은 request ID를 재사용하므로 경로를 다시 계산하지 않는다. 첫 저장 요청을 React state로 보관해 시도 전 확인과 시도 후 재확인 상태를 구분한다. 동시 클릭을 막는 기존 실행 잠금, revision·권한·감사 이력과 서버 확인 계약은 유지했다. 닫기 버튼은 보조색으로 구분해 저장 버튼과 경쟁하지 않게 했다.

서버는 추천 뒤 목록·주소·설정 등이 바뀌면 저장을 거절하며, 30분이 지난 추천도 재계산을 요구한다. 이 기존 검증은 변경하지 않았다. 운영에서 시험 추천·순서 저장·거래처 등록·재고 변경은 하지 않았다.

## 오늘 납품처가 이미 있는 경우

현재 서버의 `PlanningService.addCustomers`는 해당 직원·날짜의 최신 목록을 transaction으로 읽고 합친다. 상호 문자열 대신 연결한 customerId로 중복을 제거한다.

- 직접 저장한 오늘 목록의 기존 순서를 유지하고, 새 거래처는 뒤에 추가한다. A,B가 있고 사진이 B,C라면 A,B,C가 된다.
- 이미 등록된 곳만 다시 인식하면 오늘 목록과 revision을 불필요하게 변경하지 않는다.
- 완료 사진이 있는 거래처와 기존 재고 이력, 내 납품처와 직원별 줄임말을 보호한다. 사진에 안 보였다는 이유로 기존 오늘 항목을 삭제하지 않는다.
- 오늘 목록을 아직 저장하지 않아 내 납품처가 기본으로 보이는 경우와, 실제 저장한 오늘 목록은 구분한다. 첫 사진 등록에서 모든 내 납품처를 무조건 오늘 목록으로 가져오지 않는다. 저장된 오늘 선택이 있다면 보존한다.

권장 정책은 이 병합을 기본값으로 유지하고, 화면에서 새 연결과 이미 등록된 곳을 구분하는 것이다. 매 사진마다 확인을 받으면 연속 촬영을 방해하므로 애매한 상호 확인만 유지한다. 전체 교체가 필요하다면 별도의 `사진 기준으로 새로 정리` 동작에서 모든 사진의 분석이 끝난 뒤 제거될 목록을 검토·확인하게 한다. 한 장씩 기존 목록을 교체하면 마지막 명세서 한 곳만 남을 수 있으므로 자동 교체는 피한다. 이 추가 정책 UI는 이번 작업에서 구현하지 않았다.

## 검증

- 변경 전 새 확인 시험에서 저장 요청이 이미 발생하는 것을 모바일·PC 두 프로젝트에서 재현했다.
- 최종 동작 E2E 32개 통과. 확인 전 저장 요청0, 취소 시 기존 순서 유지, 첫·마지막 고정, 사진 완료 항목 필터, 수동 편집, 저장 실패/응답 유실 때 같은 request ID 유지와 재계산0을 포함한다.
- 마지막 보조색 적용 후 관련 E2E 6개 재확인. 390px와 320px 긴 이름 화면을 생성·시각 확인했고 페이지 오류와 가로 넘침은 없었다. 이 화면은 실제 컴포넌트와 격리된 예시 데이터다.
- 주소 관련 단위 시험은 52개 통과 뒤 Callable 파일 초기 import hook 10초 timeout이 한 번 있었다. timeout·assertion을 바꾸지 않고 해당 파일을 단독 재실행해 3개가 통과했다. 총55개 시험의 마지막 결과가 통과다.
- 기존 사진 일괄 등록 demo Firestore gate 22개 통과. 기존 목록·사진·이력 보존, 중복과 동시 병합, 다른 직원 권한, 줄임말과 원본 사진 미저장을 확인했다. 운영 데이터와 외부 AI를 쓰지 않았다. 첫 emulator 설정은 프로젝트 밖 rules 경로로 시작이 차단됐고, 격리 출력 폴더에 기존 rules를 그대로 복사한 뒤 실행했다.
- 관련 lint·전체 타입 검사, 운영 형식 build·PWA·성능·Hosting artifact gate 통과. 최초 타입 검사와 build를 동시에 실행해 `.next/types` 교체 경합이 있었고 순차 실행으로 바로잡았다. 성능 한도를 바꾸지 않고 안내를 줄여 최종 명세서·경로 JS gzip 8,186B/8,192B와 CSS raw8,071B/9,216B를 통과했다. 두 중간 후보의 용량 초과 로그는 남겼다.
- 원시 로그와 예시 화면은 git 제외 `output/route-save-confirmation/`에 보관했다. 전체 원격 CI·운영 배포·실물 휴대폰 시험은 실행하지 않았다.
